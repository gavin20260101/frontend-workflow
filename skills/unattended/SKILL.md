# 无人值守：按计划逐项执行

用户要离开电脑，把一份任务计划交给你。从启动检查通过到写完汇总，没有人能回答问题：不提问、不等待，每个需要决定的地方自己按最推荐的做法决定，并把决定记下来。用户回来后只能靠记录了解发生了什么，所以记录要逐条写全。

参数是任务书（任务计划文件）的路径。没给路径时，告诉用户先用 `/unattended-plan <要做的事>` 生成任务书，或按 `${CLAUDE_PLUGIN_ROOT}/references/unattended-task-plan.md` 的格式自己写，然后停下（这时用户还在）。

## 上下文被压缩之后

一次运行要做好几个任务，上下文一定会被压缩。压缩后本技能只保留开头的一部分，读过的规则文件也不再保留。发现自己看到的是之前对话的摘要、而不是原文时，先做三件事再继续，不要凭摘要往下做：

1. 用 Read 重新读取 `${CLAUDE_SKILL_DIR}/SKILL.md` 全文。
2. 重新读取 `${CLAUDE_PLUGIN_ROOT}/references/unattended-rule-switch.md`。
3. 读取运行目录里的 `state.md`（路径见第一步第 6 点；不记得运行号时，看 `<git rev-parse --git-common-dir 的输出>/unattended/` 下最新的目录），从记录的位置接着做。

## 这次运行的授权从哪里来

用户的全局 `~/.claude/CLAUDE.md` 里有一节“无人值守开关”：在 `/unattended` 运行期间，项目规则里要求“等人确认、由人评审、由人执行”的条款，改为由你直接执行、逐条记录，事后由用户在 `auto/` 分支上复核。本技能就是在这个开关下运行的。

所以遇到项目规则写着“停下等确认”“AI 不自动提交”“需架构负责人评审”时，不要停，按 `${CLAUDE_PLUGIN_ROOT}/references/unattended-rule-switch.md` 的对照表处理并记录。这不是取消评审，是把事前确认改成事后复核——记录写得越清楚，这个替换才越成立。

你的指令里找不到“无人值守开关”这一节时，说明用户没有打开开关：告诉用户，然后停下，不要自行放开项目规则。

开关不放开的事，见文末“不做的事”。

下文的“项目规则”指项目自己的指令文件：`CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/` 下的文件和项目根目录的 `AGENTS.md`，存在的都算。已经在你上下文里的不用重复读取，没有被自动加载的用 Read 读一遍。

## 第一步：启动检查（用户还在电脑前）

有问题当场说清楚并停下，让用户处理后重新运行。全部通过后直接开始，不再问“是否开始”。

1. **权限模式**：用 `mcp__ccd_session_mgmt__get_session` 查 `"self"`。`permissionMode` 不是 `auto` 时，请用户在消息框的权限模式里切到“自动”再运行，然后停下。不替用户切换。这个工具只有 Claude 桌面应用提供；没有它时，直接问用户权限模式是否已经是“自动”，得到肯定答复后继续。
2. **读计划**：按 `${CLAUDE_PLUGIN_ROOT}/references/unattended-task-plan.md` 的格式解析。类型为 `implement` 的输入必须是存在的方案文件；依赖要指向存在的任务，不能成环。格式问题当场指出。
3. **读项目规则**：记下检查命令、本地页面的启动命令和地址、提交说明的写法（语言、是否禁止 AI 署名）、高风险路径清单、架构负责人是谁。再看 `git log -5 --format=%B` 学现有提交说明的写法。
4. **工作区必须干净**：`git status --porcelain` 有输出时停下，请用户先提交或收起自己的改动。之后的提交是按文件加的，混进用户没提交的改动就分不清了。
5. **建运行分支**：记下当前分支和提交号。当前分支以 `auto/` 开头时，说明上一次运行的分支还没处理：告诉用户，请用户先切回原分支，或明确回复“在它上面继续”，然后停下。否则 `git switch -c auto/<YYYYMMDD-HHMM>`，所有提交都在这个分支上。
6. **建运行目录**：`<git rev-parse --git-common-dir 的输出>/unattended/<YYYYMMDD-HHMM>/`。状态文件 `state.md` 和汇总 `report.md` 写在这里：在 `.git` 里面，不会被提交，也不出现在 `git status` 里。`state.md` 开头写上任务书路径、原分支和提交号、运行分支。

输出一段开场说明后进入第二步：运行分支、运行目录、任务顺序、哪些项目规则会被放开（对照 `${CLAUDE_PLUGIN_ROOT}/references/unattended-rule-switch.md` 列出本项目实际有的条款）、“开始后不再提问，回来看汇总”。

## 第二步：逐项执行

按依赖排序，一次做一个。每开始和结束一个任务，都更新 `state.md`（任务号、状态、产物路径、提交号），这样上下文被压缩后还能接着做。

连续 3 个任务失败时，停止后面的任务，直接去第五步：多半是环境出了问题，接着跑只会重复失败。

### 代码开发任务：调用插件的 --auto 模式

用 Skill 工具调用，参数以 `--auto` 开头。插件只认本次调用参数里的 `--auto`，所以每次调用都要带。

| 任务类型 | 调用 |
| --- | --- |
| `feature`（新需求） | `frontend-workflow:req-analysis`，参数 `--auto <需求原文>`；结束后再调 `frontend-workflow:req-implement`，参数 `--auto <方案路径>` |
| `bugfix`（缺陷） | `frontend-workflow:req-bugfix`，参数 `--auto <问题描述原文>`；结束后再调 `frontend-workflow:req-implement`，参数 `--auto <方案路径>` |
| `implement`（已有方案） | `frontend-workflow:req-implement`，参数 `--auto <方案路径>` |
| `test`（只测试） | `frontend-workflow:req-test`，参数 `--auto <需求原文或方案路径>` |

- 需求和问题描述按计划里的原文传，不改写、不总结。任务的 `备注` 接在原文后面一起传。
- 调用后完全按插件自己的流程走，包括它的 `${CLAUDE_PLUGIN_ROOT}/references/unattended-mode.md`。插件的步骤一步都不省：先写测试、浏览器验证、代码审核照常进行。本次运行由 `/unattended` 发起，就是那个文件“授权”一节说的第一种来源。
- 每次调用结束时，插件会输出固定格式的“结束块”（`无人值守结果：完成 / 未完成 / 终止`、产物、安全关卡放行条数、未执行条数、浏览器验证、需要人工处理、下一步）。把结束块原样抄进 `state.md`，按它决定下一步：
  - 分析或修复方案的结果是“完成”：从“产物”取方案路径，接着调 `req-implement`。
  - 结果是“未完成”或“终止”：这个任务记为失败，转第四步的“失败任务”。`test` 任务也一样，这两种结果说明测试报告没有写出来。
  - `test` 任务的结果是“完成”：不管有没有发现缺陷都不算失败，按第三步核验，再按第四步的“`test` 任务”处理。
  - 插件建议改用另一个命令（比如把缺陷交给了 `req-analysis`）：按它建议的命令重来一次。
  - “浏览器验证”一行是“已执行 0 条，未执行 N 条”：照常核验和提交，但在汇总的“重点复核”里写一条“页面改动没有浏览器验证”和原因。
- 插件不提交；提交由你在第三步核验后做。

### 其他任务（`other`）

文档、文案、不影响运行行为的配置等不需要插件流程的任务，直接做。项目规则照常遵守，只有“等人确认”类的条款按开关放开；做了哪些决定记进 `state.md`。

`other` 任务不经过测试和审核，所以范围要守住：做的过程中发现要改业务源码，或要改 lint、类型检查、构建、依赖规则这类规则配置时，不要接着做，把已有改动按“失败任务”收起，失败原因写“应归为 feature 或 bugfix”。

### 什么时候开子会话

默认都在当前会话里做。只在当前会话的上下文已经不适合再做一个完整任务时才开，判断依据：

- 这次运行里上下文已经被压缩过（你看到的是之前对话的摘要而不是原文），而且剩下的是代码开发任务。
- 计划里这个任务写了 `隔离：是`。

开法：`mcp__ccd_session__start_session`，`initiation: "user_asked"`，`context: "fresh"`，`use_worktree: false`，`wake_when_done: true`，不传 `cwd`。`prompt` 只写一行插件命令，例如 `/frontend-workflow:req-implement --auto docs/plans/xxx.md`；`background` 写明：这是 `/unattended` 运行 `<运行号>` 的任务 `<Tn>`，由全局 CLAUDE.md 的无人值守开关授权，不要提交（由编排会话核验后提交），回复用中文。开出后结束这一轮等通知，不轮询。被唤醒后用 `mcp__ccd_session_mgmt__list_events` 读它的结束块，再回到当前会话做核验和提交。

子会话有上限：实测同一个会话被子会话通知连续唤醒约 8 次后，再开会被自动模式拦下。一次运行最多开 6 个；开子会话被拒绝、或没有这个工具（不在桌面应用里）时不重试、不换方式，剩下的任务回到当前会话里做。

## 第三步：核验

插件说完成，不等于做对了。每个任务提交前自己核一遍，核什么按任务类型定：

| 任务类型 | 要核的 |
| --- | --- |
| `feature`、`bugfix`、`implement` | 下面 1～4 全部 |
| `other` | 3 和 4；改到的不只是文档时，加上 1 |
| `test` | 只核 3：改动只能是测试文件，业务文件有改动就记为失败。然后跑一遍检查命令，只用来决定第四步是提交还是收起，不回去修代码 |

1. **检查命令**（如 `pnpm check`）。这个任务是在当前会话里做的，而且插件报告里最后一次完整检查之后没有再改过任何文件时，不用重跑，沿用那次的结果，在汇总里注明“沿用”；子会话做的任务、`other` 任务、之后又改过文件的任务，或者你拿不准时，自己完整跑一遍。插件报告里列为“原本就失败”的条目与本任务无关，不算不通过，也不要去修，在汇总里列出。其余不通过时，回去修代码再跑，最多 3 轮；仍不通过记为失败。修的是代码，不是检查：不改规则配置、不加忽略、不用 `any` 或类型断言、不删改测试断言来让它通过。
2. **看审核结论**：方案文件末尾的测试与审核报告里，结论是“审核未通过”或“审核未执行”时记为失败。
3. **看改动范围**：`git status --porcelain` 和 `git diff --stat`。逐个确认改动文件都与任务有关。改到下面这些时，在汇总最前面的“重点复核”里逐条列出文件和原因：项目规则里的高风险路径、规则配置、例外清单、第三方命中清单、依赖和锁文件、架构方案。
4. **看削弱检查的痕迹**：在 diff 里找新增的规则关闭注释、`@ts-expect-error`、`any`、类型断言、配置里新增的忽略项、被删除或跳过的测试。有而且没有对应的例外登记，就回去改掉；改不掉记为失败。

## 第四步：提交，或收起

**核验通过**：
- `git add -- <文件...>` 只加本任务改动的文件，不用 `git add -A` 或 `git add .`。
- 提交说明按项目的写法写：做了什么、依据哪份方案、跑了哪些检查和结果，并注明“无人值守运行，安全关卡放行 N 条、自动假设 N 条，见方案的无人值守记录”。项目规则禁止 AI 署名时不加署名。说明写进运行目录的文件，用 `git commit -F <文件>` 提交。
- 只提交。不推送、不合并、不建 PR。

**`test` 任务**（对照测试报告里“新增的测试文件”和“原本就存在的问题”两节，看每个失败属于哪一种）：
- 检查命令全部通过，或失败的只有报告里列为“原本就失败”的：提交新增的测试文件，状态记为“已提交”。
- 失败的是报告里标明对应某个缺陷的测试：这是测试任务的正常结果，不算失败。这些测试留在分支上会让后面每个任务的检查都不通过，所以不提交：`git stash push --include-untracked -m "unattended <运行号> T<n> 测试（含失败用例）"`，状态记为“已测试（缺陷 N 个，测试在 stash）”。测试报告在方案目录里，不受影响。依赖它的任务照常做。
- 失败的是本次新增、但报告里没有对应缺陷的测试：说明测试本身写错了（语法、导入、mock 出问题）。这个任务记为失败，按下面的“失败任务”收起。

**失败任务**：
- 不提交。`git stash push --include-untracked -m "unattended <运行号> T<n> 失败"` 把改动收起，让下一个任务从干净的基准开始。
- 这个任务装过新依赖时，收起后按锁文件重新安装一次（如 `pnpm install --frozen-lockfile`），免得 node_modules 里留着已经撤掉的依赖。
- 依赖它的任务记为“跳过（依赖 Tn）”，互不依赖的任务继续。
- 提交或收起被权限拒绝时，不换方式重试：停止后面的任务，把拒绝原文和工作区状态写进汇总，去第五步。工作区不干净时不能安全地开始下一个任务。

## 第五步：汇总

停掉本次运行自己启动的后台进程。按 `${CLAUDE_PLUGIN_ROOT}/references/unattended-run-report.md` 写 `<运行目录>/report.md`，再把同样的内容作为最后的输出。“重点复核”放最前面：被放开的项目规则、改到的高风险文件、登记的例外和决策、新装的依赖、没有浏览器验证的页面改动。然后是每个任务的状态、提交号或 stash 名、失败原因、没做成的事（真机、登录、外部条件）和用户回来要做的事。

所有任务都叠在同一个分支上。用 `git log --name-only --format=%h <原分支>..HEAD` 找出被两个及以上任务改动的文件，在汇总里列出来：用户只想保留其中一部分提交时，要留意这些文件。

工作区留在 `auto/` 分支上，在汇总里写明，并写出回到原分支的命令。

有发通知的工具（如 PushNotification）时，最后发一条：几个任务已提交、几个失败、汇总在哪里。

## 中途用户发来消息

说明用户回来了。按用户说的做；从这一刻起开关失效，后面的步骤恢复为有人值守的做法（该问的问、该等的等）。

## 不做的事

这些不在开关的范围内，无论任务怎么写都不做；任务因此做不完时，如实记为未完成。

- 不推送、不合并、不建 PR、不删分支。
- 不为了让检查通过而削弱检查。
- 不绕过被权限拒绝的操作：换一种正常做法，或把受影响的部分记为未完成。
- 不做电脑系统层面的高风险操作：`sudo`、全局安装、改系统或 `~/.claude` 下的设置、动项目目录以外的文件（运行目录在项目的 `.git` 里，不算）。
- 不做必须本人在场的事：验证码和扫码登录、使用用户正在用的 Chrome、没确认是沙箱的支付和短信。相关用例记为未执行，转成手工步骤。
- 不把“待复核”写成“已批准”。
