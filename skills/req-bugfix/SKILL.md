# 缺陷分析与修复方案

用户调用本命令时附带的文字，就是问题原文。如果没有附带任何文字，请用户提供问题描述（现象、复现步骤、期望结果、环境），然后停下。内容是新功能或需求变更、而不是缺陷时，提示用户改用 /req-analysis，然后停下。

核心原则：**先复现、再找根因、最后才定修法**。根因没有证据之前，不要提出修复方案。

Superpowers 可用时，问题涉及复杂调用链、环境差异或连续修复失败，先使用 `superpowers:systematic-debugging` 完成根因调查，再给出修复方案。保留本技能的前端复现、浏览器证据和缺陷方案；不再额外调用 brainstorming/writing-plans 生成重复文档。修复阶段由 `/req-implement` 对行为测试执行 RED-GREEN。

分两个阶段进行，**每个阶段结束后都必须停下来，等待用户回复**；小问题可以合并为一次，见阶段一的结束规则。

全程只读，不修改任何业务代码、测试代码或配置文件。唯一允许写入的是阶段二末尾的方案文件（docs/plans/ 目录下）、“保存方案文件”一节中说明的本机 git exclude 文件，以及复现问题时浏览器测试子代理保存在 docs/plans/browser-artifacts/ 下的截图。

下文的“项目规则”指项目中的 CLAUDE.md 和 CLAUDE.local.md（存在时）。

## 并行工作区（worktree）

参数以 `--worktree` 或 `--worktree=<名字>` 开头时（/req-parallel 生成的第一条消息会带上它），先把本会话放进独立的 git worktree。参数中还可以带 `--base=<分支或提交>` 指定起点。去掉这两个参数后，剩下的才是问题原文：

1. 运行 `git rev-parse --git-dir` 和 `git rev-parse --git-common-dir`，两者不同说明已经在 worktree 中，跳过第 2～4 步。
2. 确定起点：参数中有 `--base` 时用它；没有时停下来，请用户在以下选项中选择，然后等待回复——
   - 远端默认分支：运行 `git symbolic-ref --short refs/remotes/origin/HEAD` 得到名字；取不到时不列这一项。
   - 当前分支：运行 `git rev-parse --abbrev-ref HEAD` 得到名字。
   - 其他分支或提交：由用户输入。
   用 `git rev-parse --verify <起点>^{commit}` 确认起点存在，记下提交号；不存在时请用户重新选择。当前目录有未提交的改动时提醒用户：这些改动不会带进 worktree。
3. 用 `git worktree list` 查看 `.claude/worktrees/<名字>` 是否已经存在，然后用 EnterWorktree 工具进入：已存在时传 `path` 进入它，并告诉用户这是继续使用已有的 worktree，跳过第 4 步；不存在时传 `name` 创建并进入。名字用参数中给出的；没有给出时用 `bug-<简短英文名>`（小写英文和连字符）。没有 EnterWorktree 工具时，请用户新开一个会话、打开输入框下方的 Worktree 开关后再运行本命令，然后停下。
4. 对齐起点（只针对第 3 步新建的 worktree）：运行 `git rev-parse HEAD`，与第 2 步记下的提交号相同就结束这一步。不同时，先确认 `git status --porcelain` 没有输出，再运行 `git reset --hard <记下的提交号>`，把这个新 worktree 的分支移到所选起点（只影响这个刚建好、还没有任何改动的 worktree；这个命令会请用户确认），完成后再用 `git rev-parse HEAD` 核对。`git status --porcelain` 有输出时不要执行，停下来说明情况。

只要当前在 worktree 中（包括用户用 Worktree 开关开的会话，判断方法同第 1 步），开始分析前先做环境检查：
- 本机 git exclude 中要有 `/.claude/worktrees/` 这一行：没有就按“保存方案文件”中追加 exclude 的方式追加（用文件编辑工具，已有就不追加），避免主目录把 worktree 当成未提交的改动。
- worktree 根目录下要有 node_modules：没有时给出命令（`cd <worktree 路径>`，再加上包管理器的安装命令，如 `pnpm install`），请用户在终端执行后回复，然后停下。不要自己安装。
- 访问端口：取本 worktree 在 `git worktree list` 中的序号 n（主目录为 0），建议端口为项目默认端口加 n（Vite 默认 5173），之后请用户启动本地页面时给出带端口的命令（如 `pnpm dev --port 5174`）。实际地址以用户启动后告知的为准。
- 方案“浏览器功能测试”的环境中写明 worktree 路径、分支名和实际访问地址。

输出要求：
- 复现结论、根因、影响范围中的每条结论，都按项目规则标注证据等级（A/B/C）。证据等级是唯一使用 A/B/C 的地方，修改的确定程度用“确定 / 可能 / 待定”。
- 项目规则没有定义证据等级时，使用默认定义：A = 打开文件看到了代码（附路径 + 函数名 + 行号）；B = 推断（写明依据和缺失的环节）；C = 代码中无法确定，需要向人确认。
- 证据等级为 C 的结论，同时列入待确认事项（Q 编号）。
- 每个阶段的输出末尾，列出实际打开过的文件和执行过的搜索（关键词 + 路径），以及查询过的第三方库文档（库名 + 版本 + 问题），放在该阶段规定的结束语之前。

## 查询第三方库文档

结论涉及第三方库（框架、组件库、工具库）的 API、配置项或版本差异时，如果可以使用插件自带的 Context7 服务（工具 `resolve-library-id`、`query-docs`），先查询：

- 版本以项目 package.json 中声明的为准，查询时带上版本。
- 查询内容只写库名、版本和通用的技术问题，不写业务代码、内部接口地址、业务名称或任何账号信息。查询会发送到 Context7 的服务器。
- 在结论中注明文档出处（库名 + 版本 + 文档条目）。文档说明的是库的行为，项目中的实际用法仍要打开代码确认，证据等级按项目规则标注。
- Context7 不可用（未连接、超出调用额度、查不到对应版本）时照常分析，在结论中注明“未查到对应版本文档”，不要凭记忆写成确定的结论。

## 阶段一：复现与根因

输出以下内容：

1. 问题复述：一两句话说明现象。
2. 复现信息：环境（设备、系统、浏览器或 App 版本）、复现步骤、实际结果、期望结果、出现频率。缺少会影响定位的信息时，列为待确认事项。
3. 复现：
   - 问题出现在页面上、且能在浏览器中模拟时：请用户启动本地页面（给出启动命令和访问地址），停下等用户确认已启动；需要登录信息时向用户索取，只在调用子代理时传入，不写入任何文件。然后调用本插件的 req-browser-tester 子代理（在可用代理列表中显示为 `<插件名>:req-browser-tester`），模式为“复现”，提供访问地址、复现步骤（含实际结果和期望结果）、设备与浏览器服务、登录方式和登录信息。
   - 设备与浏览器服务：按项目规则和缺陷影响的平台选择无头、隔离的浏览器——iOS 用 browser-ios，Android 用 browser-android；只有缺陷影响两端时才都覆盖。想看着复现过程、或需要在页面上手动登录一次后保留登录态时，用 browser-chrome（本机 Chrome 窗口 + Pixel 7 模拟，测试专用配置）。必须复用用户日常 Chrome 中已有的登录态（例如公司 SSO）时，用 browser-user-chrome：先说明将在用户的 Chrome 中操作哪个地址并征得同意，提醒用户确认已安装 Playwright Extension、连接时在授权页中选择标签页；同意后，调用时说明“用户已同意使用 browser-user-chrome”。
   - 复现报告中的“需要用户协助”不是“无”时（例如需要登录、出现验证码或 SSO 页面、页面打不开、工具调用被拒）：立即停下，按 H 编号逐条告诉用户看到了什么、需要做什么、做完后回复什么，等用户回复。用户提供的登录信息同样只在调用子代理时传入。然后以“继续”模式调用同一个子代理，附上原来的全部输入、每条 H 的处理结果，以及已有结果的设备。不要把这种情况记为“未复现”；只有用户明确表示不处理时，才按用户的决定记录。你自己的工具调用被权限确认拒绝时，同样停下来询问用户。
   - 只在真机、App 内嵌 WebView 或特定线上数据下出现、浏览器中无法模拟时：写明原因，依据用户提供的信息继续分析。
   - 与页面无关的问题（如纯数据处理）：可以不在浏览器中复现，在根因中用代码和已有测试说明。
   - 复现结论记为以下之一：已复现（附截图路径，以及子代理发现的控制台报错、失败请求等线索）/ 未复现（列出尝试过的条件）/ 只能真机复现 / 不适用（说明原因）。
   - 未复现时停下，列出尝试过的条件，请用户补充复现信息。不要在没有复现、也没有其他证据的情况下推测根因。
4. 根因：从现象出发追踪调用链，写明出问题的代码位置（文件:行号）、为什么会出现、触发条件，每条结论标注证据等级。根因只有 B 级证据时，写明缺失的环节，以及实现阶段怎样补足（例如回归测试在修复前失败）。能用 `git log -S <关键代码>` 或 `git log -L` 找到引入问题的提交时，写明提交号和当时的改动。
5. 验收标准：编号列出（AC1、AC2……），写成“当……时，应该……”的形式。AC1 固定为“按复现步骤操作时，应该出现期望结果”；同一根因导致的其他表现，各写一条。
6. 待确认事项：编号列出（Q1、Q2……），每一项写成需要向产品、后端或报告人确认的具体问题。没有待确认事项时写“无”。
7. 影响范围：同一根因还会影响哪些地方（同样的写法、共用的函数或组件），以及是否影响埋点、公共接口、存储格式。
8. 测试现状：查看 package.json 和已有测试文件，说明项目用的测试框架（如 Jest / Vitest）、测试文件的存放位置和命名习惯，以及出问题的代码目前有没有测试覆盖。如果项目没有测试框架，直接写明。
   可用的检查命令：逐个读出 test / lint / typecheck / build 等脚本的原文，并判断——
   - 包管理器：以项目规则中的声明为准；没有声明时，看根目录存在哪个锁文件（只看是否存在，不读取内容）。
   - 会修改文件的脚本（含 --fix、--write、-u、--updateSnapshot 等参数，包括通过 run-s / run-p 间接调用的子脚本）：不能作为检查命令，单独列出。
   - 会进入 watch 或常驻的脚本（如不带 run 的 vitest、jest --watch、react-scripts test、dev / serve）：写出单次运行的写法，优先加 `CI=true` 前缀，或追加单次运行参数（如 vitest 的 `--run`、jest 的 `--watchAll=false`）；脚本里写死了 watch、无法单次运行的，单独列出。
   浏览器测试条件：
   - 项目是否已有 E2E 框架（Playwright Test、Cypress 等的配置文件和依赖）及其单次运行脚本。
   - 启动本地页面的脚本（如 dev）和访问地址（看构建配置中的端口；Vite 默认为 http://localhost:5173）。
   - 出问题的页面是否需要登录，登录态从哪里来（页面登录、注入 token、开发环境免登录）。
   - 接口数据来自测试环境、本地 mock，还是需要在浏览器中拦截模拟。
   - 哪些功能依赖 App 环境（如 JSBridge、App 内登录），只能在真机上验证。
   拿不准的写成待确认事项。
9. 风险等级（初评）：逐项对照以下维度，取最高的一项作为等级——
   - 修改范围：单文件（L1）/ 同一模块内（L2）/ 跨模块（L3）
   - 是否触及项目规则中列出的高风险区域（把待修改的文件路径逐个与清单匹配）：是即为 L3。项目规则中没有高风险区域清单、清单为空或仍是待填写状态时，写明“项目未配置高风险区域”，不要当作未触及
   - 埋点：修改已有的事件名或属性名为 L3，新增为 L2
   - 用户感知：几乎无感（L1）/ 可感知（L2）/ 核心流程（L3）

阶段一结束时：
- 小问题合并：风险等级为 L1、没有待确认事项、根因有 A 级证据、复现结论不是“未复现”时，不在这里停下，直接输出阶段二，只在阶段二结束时停一次。
- 有待确认事项：说明“请提供待确认事项的答复，之后进入阶段二。暂时无法确认的条目，可以回复‘按假设处理’。”
- 没有待确认事项：说明“请确认根因和验收标准，之后进入阶段二。”

## 处理用户的答复

- 每条待确认事项的状态记为以下三种之一：
  - 已答复：记录答复内容。
  - 按假设处理：用户明确同意先按假设推进时，写明“假设：……（待确认）”，以及假设不成立时需要改动的地方。
  - 未答复：用户没有回应，也没有同意按假设处理。
- 存在“未答复”的条目时，不进入阶段二，列出这些条目，请用户答复或同意按假设处理，然后停下。
- 不要自行把未答复的条目当作假设处理。
- 复现结论为“未复现”、用户补充了信息时：按新的信息重新复现，再继续阶段一的第 4～9 项。

## 阶段二：修复方案

在所有待确认事项都为“已答复”或“按假设处理”，且阶段一的第 1～9 项都已输出之后进行。

开头先列出“需要特别确认的事项”：方案涉及项目规则中的高风险区域、需要新增依赖（包括测试库和 E2E 框架）、修改公共接口，检查命令中有会修改文件、无法单次运行的脚本，浏览器测试需要的登录信息、测试数据、测试环境无法自动准备，或者浏览器测试需要使用你正在用的 Chrome（browser-user-chrome）时，逐项说明原因。没有就写“无”。项目没有测试框架时，不要自行安装，而是在这里提出，等用户决定。

然后输出：

0. 风险等级复核：结合答复重新评估风险等级。与初评不同时说明原因，之后一律以复核后的等级为准。
1. 修复目标：对应哪几条验收标准，根因怎样被消除。修的是根因，不是只处理表面现象；只能先处理表面现象时，说明原因和后续怎样根治。
2. 修改的文件：逐个列出，说明改什么、为什么改、大致改几行。
3. 不做什么：明确排除的内容，包括影响范围中决定不在本次修的地方。
4. 修复方式的取舍：L2 及以上至少比较一种其他修法（例如在源头修复与在调用方兜底），说明为什么不选；L1 写“不适用”。
5. 兼容性风险：L2 及以上必须填写（老数据、老版本 App、其他调用方、数据团队的报表）；L1 写一句话或“不适用”。
6. 埋点变更：涉及埋点时，逐条列出新增或修改的埋点——事件名、属性、触发时机，以及是新增还是修改已有埋点；修改已有事件名或属性名时，说明影响的报表。没有就写“无”。
7. 测试方案（必须具体到用例）：
   - 回归测试（先失败后通过）：问题原文中写了“已有失败的回归测试”（通常来自 /req-test 的测试报告）时，先阅读该测试文件，核对这条用例：断言写的是修复后的期望结果，覆盖了复现步骤，失败摘要与实际结果一致。核对通过就沿用它：列出文件路径、用例名和运行命令，标注“沿用（来自 <测试报告路径> 的 <缺陷编号>）”，不再另写同样的用例；同一根因的其他表现仍要补充用例。核对不通过的，写明原因，按下面的要求另写。文件在当前目录中不存在（例如在新的 worktree 中，没有提交的文件不会带过来）时，按该用例的描述列为新用例，并注明来源。能用单元测试或组件测试复现问题时，列出测试文件路径（沿用项目已有的目录和命名习惯）和用例；项目已有 E2E 框架且适合在真实页面复现时，沿用框架新增 E2E 用例，列出文件路径和单次运行命令。每个用例写明用例名、AC 编号、前置条件或 mock、输入、修复前的实际结果、修复后的期望结果。实现阶段会先由对应子代理写好用例，确认它在修复前失败，再动手修复。无法自动化时写“不适用”并说明原因，以浏览器复现作为修复前的证据。
   - 浏览器功能测试：问题与页面无关时写“不适用”。否则写明：
     - 方式：“E2E 脚本”（项目已有 Playwright Test 等框架时，沿用其目录和写法新增用例，列出文件路径和单次运行命令）/“浏览器验证”（项目没有 E2E 框架时，由浏览器测试子代理用插件自带的浏览器工具逐步执行，不新增依赖）。
     - 环境：访问地址；启动命令（由用户在测试前手动启动，流程不会自行启动）；登录方式（只写方式，不写账号、密码或 token 本身）；测试数据和接口来源；需要在浏览器中模拟的接口返回（如空数据、接口失败、慢接口）。
     - 设备与浏览器服务：只为产品支持且受缺陷影响的平台指定，按风险选择覆盖范围；iOS 用 browser-ios，Android 用 browser-android，只有缺陷影响两端时才都覆盖。用到 browser-user-chrome 时列入“需要特别确认的事项”。模拟环境不能代替真机，差异项放到手工测试步骤。
     - 用例：至少包含按复现步骤操作的用例（修复后应出现期望结果），以及同一页面上相关功能的回归用例。每个用例写明用例名、对应的验收标准编号、设备、前置条件、操作步骤、预期结果（页面上可见的状态）、需要核对的埋点请求（事件名和关键属性）。
     - 通用检查（每个用例都会做，不用逐条写）：控制台没有报错、没有意料之外的失败请求、页面没有横向溢出；移动端还会检查本次改动涉及的可点击元素尺寸。
     - 性能与弱网检查（可选）：问题与加载慢、弱网、卡顿或内存有关，或风险等级为 L3 时写，由 browser-perf 服务执行。写明页面和操作、网络条件和 CPU 降速倍数、关注的现象和指标（LCP、INP、CLS，不降速时的参考值为 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1）、是否检查内存泄漏。开发服务器没有打包压缩，测得的指标只能看相对变化；需要准确数值时，写明使用构建后的预览页面及其启动命令和地址，同样由用户手动启动。
   - 检查命令：列出实现阶段要执行的完整命令（包括单次运行写法），只能基于 package.json 中已有的脚本。会修改文件或无法单次运行的脚本不列入，放到“需要特别确认的事项”。E2E 命令写在浏览器功能测试中，不放在这里。
   - 手工测试步骤：只列自动化测试（包括浏览器功能测试）覆盖不到的部分；复现结论为“只能真机复现”时，必须列出真机上的复现与验证步骤。编号列出操作步骤和预期现象，写明需要在哪些环境验证。
   - 回归场景：L2 及以上必须列出；L3 必须覆盖所有受影响的调用方。
   - 基于假设的部分：如果有“按假设处理”的条目，说明假设不成立时哪些用例需要调整。
8. 回滚方式。
9. 可选的局部整理与技术债：单独列出，不放进修改范围。

## 保存方案文件

方案输出后，将完整方案写入 `docs/plans/YYYYMMDD-fix-简短英文名.md`（日期为当天，英文名用小写和连字符，例如 `20261031-fix-order-list-duplicate.md`）。目录不存在就创建；同名文件已存在且不是本问题的方案时，在文件名末尾加 `-2`、`-3`，不要覆盖。

写入前，先判断方案文件会不会被提交进仓库（以下 git 命令都是只读的）：
1. 运行 `git rev-parse --is-inside-work-tree`。失败说明不是 git 仓库：跳过本判断，在输出中注明。
2. 运行 `git ls-files -- docs/plans/`。有输出说明该目录已有文件被仓库跟踪：不要修改 git 配置，也不要执行 git rm，停下来告诉用户“docs/plans/ 已被仓库跟踪”，由用户决定是否继续写入。
3. 运行 `git check-ignore -q docs/plans/<文件名>.md`（文件还不存在也可以判断）：
   - 退出码 0：已被忽略，直接写入。
   - 退出码 1：未被忽略。运行 `git rev-parse --show-prefix` 和 `git rev-parse --git-path info/exclude`，用文件编辑工具（不用 echo 等终端命令）在 exclude 文件末尾追加一行 `/<前缀>docs/plans/`：前缀为空时就是 `/docs/plans/`；文件不存在就新建；已有相同的行就不追加；不改动原有内容。然后再运行一次 check-ignore，确认退出码为 0，并在输出中说明“已在本机 git exclude 中忽略 docs/plans/，只影响本机，不修改 .gitignore”。

文件开头写明状态和类型：
- `状态：含待确认项`：存在“需要特别确认的事项”，且用户尚未确认。
- `状态：待审批`：其他情况。
- `类型：缺陷修复`。

文件必须包含以下章节，供 /req-implement 读取：

- 状态和类型
- 问题原文
- 现象与复现（复现信息、复现结论和证据）
- 根因
- 验收标准（AC 编号）
- 待确认事项及答复（Q 编号，逐条写明状态：已答复 + 答复内容，或按假设处理 + 假设内容）
- 影响范围
- 风险等级（初评、复核结果及依据）
- 测试现状
- 需要特别确认的事项
- 阶段二的全部内容（0～9 项）
- 方案依据的代码版本：执行 `git rev-parse --short HEAD` 记录当前提交号；不是 git 仓库时写“无（非 git 仓库）”

用户对方案提出修改意见时，更新同一个文件，不要新建。用户确认了“需要特别确认的事项”后，把状态改为 `待审批`。

## 方案审核

方案文件首次保存后，按 `references/plan-review.md` 调用 req-plan-reviewer 审核一轮并处理意见，然后再给出阶段二的结束语。

阶段二结束时，说明：
“方案已保存到 <文件路径>。请审阅方案，批准后在新会话或当前会话中运行 /req-implement <文件路径> 开始修复。修复前会先确认回归测试在修复前失败。在此之前，我不会修改任何代码。”

如果状态为“含待确认项”，改为说明：
“方案已保存到 <文件路径>，其中有需要特别确认的事项（见开头）。请先确认这些事项，我会更新方案状态，之后才能运行 /req-implement。”
