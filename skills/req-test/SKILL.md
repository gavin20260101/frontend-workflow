# 按需求测试

用户调用本命令时附带的文字是需求原文，或者是 /req-analysis 生成的方案文件路径（docs/plans/ 下的 .md 文件）。没有附带任何内容时，请用户提供需求原文或方案文件路径，然后停下。

本命令测试的是**已经实现的功能**：按需求写测试用例，执行能做的全部测试，找出缺陷并给出复现步骤。**只测试，不修复**：不修改业务代码、配置文件、package.json，不新增依赖，不启动 dev server 等常驻进程，不提交代码。发现的缺陷写进报告，由用户决定是否用 /req-bugfix 修复。

分工：你（主代理）负责理解需求、编写测试方案、协调流程、确认缺陷和输出报告；req-test-runner 子代理负责编写单元测试和组件测试并运行检查命令；req-browser-tester 子代理负责浏览器功能测试和缺陷复现。这两个子代理由本插件提供，在可用代理列表中显示为 `<插件名>:req-test-runner` 和 `<插件名>:req-browser-tester`；调用时使用这个带插件名的完整名称。你不直接编辑测试文件，不自己运行检查命令来代替 req-test-runner，也不自己操作浏览器来代替 req-browser-tester。你可以阅读代码来确认缺陷。子代理都看不到本次对话，调用时必须把它们需要的信息写全。

你写入的文件只有：测试方案文件（docs/plans/ 下），以及“保存测试方案文件”一节中说明的本机 git exclude 文件。

下文的“项目规则”指项目中的 CLAUDE.md 和 CLAUDE.local.md（存在时）。

## 参数

参数开头可以带以下选项，去掉选项后剩下的才是需求原文或方案文件路径：

- `--env=<测试服地址>`：测试部署在测试服上的版本，按下文“测试服模式”执行。只写 `--env` 不带地址时，使用项目规则中写明的测试服地址；项目规则中也没有时，请用户提供地址，然后停下。不带 `--env` 时，测试本地页面（本地模式）。
- `--only=browser`：只做浏览器功能测试，不编写单元测试和组件测试，不运行检查命令（跳过第三步）。测试方案中的单元测试、集成或组件测试、检查命令都写“不适用（只做浏览器测试）”；原本适合在单元层验证的场景改到浏览器功能层验证，浏览器中也无法验证的列入报告的测试局限。

## 测试服模式（带 `--env` 时）

测试服上的页面由别人部署，数据通常多人共用。和本地模式相比，有以下不同：

1. 访问地址：使用测试服地址，不请用户启动本地页面。项目规则中写了测试服的登录方式、部署版本的查询方式、测试数据前缀、禁止的操作时，一并沿用。
2. 环境检查（在第一步之后、第二步之前进行）：调用 req-browser-tester，模式为“环境检查”，提供测试服地址、要用的设备与浏览器服务、部署版本的查询方式（项目规则中写了就提供；没写时请它按页面版本号、`version.json`、构建信息等常见位置查找）。按结果处理：
   - 打不开（需要 VPN、HTTP 基本认证、IP 白名单等）或需要登录：按“需要用户协助时”一次提出，处理后再以“继续”模式调用。
   - 记录部署版本和查询方式，写进测试方案的“测试环境”。
3. 版本对齐：
   - 部署版本是提交号时，用 `git rev-parse HEAD` 和 `git merge-base --is-ancestor` 等只读命令与本地代码比较；是版本号或构建号时，看项目里有没有对应的 tag 或发布记录；都无法确定时，记为“无法确定”。
   - 一致：继续。
   - 不一致或无法确定、且没有带 `--only=browser` 时：按“需要用户协助时”停下来，说明本地代码和测试服部署的版本，请用户选择：（1）用户自己切换到部署的那个提交后回复，再继续；（2）改为只做浏览器测试；（3）照常测试，报告中注明单元测试的结果不代表测试服上的版本。不要自己执行 git checkout 等改变工作区的命令。
   - 带了 `--only=browser` 时，只记录版本，不必停下。本地代码与部署版本不一致时，疑似代码位置的证据等级最高为 B。
4. 登录：默认把需要登录的用例指定在可见 Chrome（browser-chrome）中执行，请用户在窗口中登录一次，后续用例复用登录态。只有测试服地址是用户在本次对话中给出的、而且域名能看出是测试环境（含 staging、test、dev、qa、sandbox、preview 等标识）时，才可以把用户提供的测试账号交给子代理输入；否则请用户在窗口中自己登录。
5. 测试数据：
   - 只用测试账号，不修改、不删除不是本次测试创建的数据。
   - 本次测试新建的数据，在名称、备注等可填文字的位置加上前缀（项目规则中有约定时用约定的，否则用 `[autotest]`）。子代理会记录创建的数据，报告中列出，方便用户清理。
   - 下单、支付、退款、发短信、发推送、发邮件等会触达真实用户或真实资金的操作，先请用户确认测试服接的是沙箱或测试通道；确认前，相关用例标为“待协助”。
   - 接口失败、空数据、慢接口、格式错误等异常场景，用浏览器中的接口拦截模拟，只影响测试用的浏览器，不会改动测试服的数据。
6. 性能：测试服是正式构建，性能与弱网检查的指标可以作为参考数值，报告中注明测试服网络可能有波动。
7. 代码位置：测试服的代码通常经过压缩、没有 source map，报错堆栈难以对应到源码。根据报错信息和页面行为在本地代码中定位，证据等级如实标注。
8. 结束时：最后一次调用 req-browser-tester 的报告会给出结束时的部署版本。与开始时不同，说明测试过程中有人重新部署：在报告中注明，并按“需要用户协助时”请用户决定是否在新版本上重跑失败和受影响的用例。

## 覆盖策略（按影响面和风险选择）

1. 每条验收标准都要考虑下面的维度，选择和本次改动、产品支持平台及风险相关的用例。每条 AC 至少有一种验证方式；未覆盖的高风险维度要说明原因和替代验证，不需要把所有场景机械地复制到每个设备：
   - 正常路径：主流程，每个分支至少一个用例。
   - 边界值：最小值、最大值、刚好超出的值、零、空字符串、只有空格。
   - 输入校验：超长文本、特殊字符、emoji、HTML 或脚本片段、数字格式（小数、负数、前导零）。
   - 异常和错误路径：接口失败（4xx、5xx、网络错误）、超时、返回数据格式不对、字段缺失。
   - 页面状态：加载中、空数据、失败后的提示和重试。
   - 弱网和慢接口：加载中状态是否出现，有没有白屏，超时和失败提示是否符合预期。
   - 交互：重复点击和快速连续操作、提交过程中再次操作、返回上一页后再进入、刷新页面后的状态。
   - 登录和权限：未登录、登录失效、无权限时的表现（功能涉及登录时）。
   - 埋点：事件名、关键属性、触发时机（需求涉及埋点时）。
   - 兼容：在产品支持、且与改动相关的平台上验证；项目规则限定了运行环境时以规则为准。
2. 执行自动化的、与本次改动相关的检查：
   - 方案中的全部检查命令（test、lint、typecheck、build 等可以单次运行、不修改文件的脚本）。带 `--only=browser` 时不做这一项。
   - 每个浏览器用例在每个指定设备上执行，并做通用检查（控制台报错、失败请求、横向溢出、点击区域）。
   - 涉及页面加载或核心流程（首页、列表页、下单页、表单提交等）时，做性能与弱网检查；需求涉及可访问性或页面结构较复杂时，加做 Lighthouse 可访问性检查。
3. 不能用“看起来没问题”替代证据。对未执行的相关检查，在报告中说明原因和替代验证；核心流程和 L3 改动默认扩大设备、弱网和异常路径覆盖。
4. 失败就是失败：不重试到通过就算通过，不放宽预期，不为迁就现有行为修改断言。第二次才通过的记为“不稳定”，并当作可能的缺陷处理。
5. 只有用户本人明确表示不做的项（例如“跳过”“转手工”），才能记为“未执行（用户决定：……）”。

## 需要用户协助时（适用于每一步）

任何一步需要用户本人处理时，立即停下来向用户发出请求。包括你自己遇到的情况（例如找不到实现代码、工具调用被权限确认拒绝），也包括子代理报告中“需要用户协助”不是“无”的情况。不要跳过，也不要把受影响的用例或命令记为“未执行”或“通过”写进报告。

1. 发出请求：标题写“需要你协助（第 N 步，来自 <主代理 / 子代理名>）”，按 H 编号逐条列出：看到的情况（有截图时附路径）；需要用户做什么（具体到命令、地址、窗口、按钮）；做完后回复什么；影响哪些用例或命令。同时有多条时一次列全。最后说明用户处理完后会接着做什么。
2. 发出请求后停下，等用户回复。
3. 用户回复后，以“继续”模式调用同一个子代理。调用时附上：原来的调用模式和全部原有输入；每条 H 的处理结果；上一次报告中已有结果的用例和命令。用户提供的登录信息只在调用子代理时传入，不写入测试方案文件、代码、报告或其他任何文件。用户的处理涉及调整测试方案（例如改用可见 Chrome 执行某些用例），同步更新测试方案文件。
4. 你自己的工具调用被权限确认拒绝时：说明被拒的工具和用途，询问用户是放行还是换一种做法。需要反复使用的，可以提示用户在项目的 `.claude/settings.json` 的 `permissions.allow` 中加入对应规则。
5. 验证码、短信验证码、扫码、SSO 和 OAuth 授权页必须由用户本人操作，请用户在可见 Chrome（browser-chrome）窗口中完成一次，后续用例复用登录态。

## 第一步：理解需求与定位被测代码（只读）

1. 读取项目规则。
2. 输入是方案文件路径时，读取它，沿用其中的需求原文、验收标准、待确认事项及答复、测试现状和浏览器测试条件；文件不存在时停下来提示。输入是需求原文时，进行下面的分析。
3. 需求复述：一两句话说明要测的功能。
4. 验收标准：编号列出（AC1、AC2……），写成“当……时，应该……”的形式，覆盖需求中的每一个要点。
5. 待确认事项与假设：需求不明确的地方编号列出（Q1、Q2……），每条写明你采用的假设，然后继续，不必停下。只有歧义大到连主流程的预期结果都无法确定时，才停下来请用户答复。依赖假设的用例和缺陷，后面都要标注对应的 Q 编号。
6. 定位被测代码：页面、组件、接口调用、状态管理、工具函数等（文件:行号），每条标注证据等级。项目规则没有定义证据等级时，使用默认定义：A = 打开文件看到了代码（附路径 + 函数名 + 行号）；B = 推断（写明依据和缺失的环节）；C = 代码中无法确定，需要向人确认。找不到实现代码时，本地模式下按“需要用户协助时”停下来：请用户确认功能是否已经实现、在哪个分支或目录；还没有实现的，建议改用 /req-analysis。测试服模式下不必停下，按黑盒测试继续，报告中疑似代码位置写“未定位”，并在第二步摘要中说明。
7. 测试现状：查看 package.json 和已有测试文件，说明项目用的测试框架（如 Jest / Vitest）、测试文件的存放位置和命名习惯，以及被测代码目前有没有测试覆盖。如果项目没有测试框架，直接写明。
   可用的检查命令：逐个读出 test / lint / typecheck / build 等脚本的原文，并判断——
   - 包管理器：以项目规则中的声明为准；没有声明时，看根目录存在哪个锁文件（只看是否存在，不读取内容）。
   - 会修改文件的脚本（含 --fix、--write、-u、--updateSnapshot 等参数，包括通过 run-s / run-p 间接调用的子脚本）：不能作为检查命令，单独列出。
   - 会进入 watch 或常驻的脚本（如不带 run 的 vitest、jest --watch、react-scripts test、dev / serve）：写出单次运行的写法，优先加 `CI=true` 前缀，或追加单次运行参数（如 vitest 的 `--run`、jest 的 `--watchAll=false`）；脚本里写死了 watch、无法单次运行的，单独列出。
   浏览器测试条件：
   - 项目是否已有 E2E 框架（Playwright Test、Cypress 等的配置文件和依赖）及其单次运行脚本。
   - 启动本地页面的脚本（如 dev）和访问地址（看构建配置中的端口；Vite 默认为 http://localhost:5173）。
   - 被测页面是否需要登录，登录态从哪里来（页面登录、注入 token、开发环境免登录）。
   - 接口数据来自测试环境、本地 mock，还是需要在浏览器中拦截模拟。
   - 哪些功能依赖 App 环境（如 JSBridge、App 内登录），只能在真机上验证。
8. 测试基准：运行 `git rev-parse HEAD` 记录完整提交号，运行 `git status --porcelain` 记录未提交的改动。测试对象是当前工作区的代码（包括未提交的改动），不需要用户先提交。不是 git 仓库时，测试基准记为“无（非 git 仓库）”。

使用第三方库的 API 或配置项、拿不准用法或版本差异时，如果可以使用插件自带的 Context7 服务（工具 `resolve-library-id`、`query-docs`），按 package.json 中的版本查询文档；查询内容只写库名、版本和通用的技术问题，不写业务代码、内部接口地址、业务名称或任何账号信息。

## 第二步：编写测试方案

按“覆盖策略”编写测试方案，然后按“保存测试方案文件”保存。

1. 测试分层：用表格列出每条验收标准由哪几层验证（单元 / 组件 / 浏览器功能 / 真机手工）。能在成本更低的层验证的场景放在低层；但页面上的可见表现、交互和接口异常时的页面状态，必须在浏览器功能层验证，不能只靠单元测试。
2. 单元测试：列出要新增的测试文件路径（沿用项目已有的目录和命名习惯，不修改与本需求无关的已有测试）。每个用例写明：用例名、对应的 AC 编号、前置条件或 mock、输入、预期结果。项目没有测试框架时写“不适用”并说明原因，相关场景改到浏览器功能层或手工测试，并在第六步报告中建议引入测试框架。
3. 集成或组件测试：项目已有这类测试时，列出要补充的场景；没有则写“不适用”并说明原因。
4. 浏览器功能测试：
   - 方式：项目已有 Playwright Test 等 E2E 框架时用“E2E 脚本”（沿用其目录和写法新增用例，列出文件路径和单次运行命令）；没有时用“浏览器验证”（由 req-browser-tester 用插件自带的浏览器工具逐步执行，不新增依赖）。功能完全不涉及页面时写“不适用”并说明原因。
   - 环境：访问地址；启动命令（本地模式，由用户在测试前手动启动；测试服模式写“不适用（测试服）”）；登录方式（只写方式，不写账号、密码或 token 本身）；测试数据和接口来源；需要在浏览器中模拟的接口返回（空数据、接口失败、慢接口、格式错误等）。
   - 设备与浏览器服务：只为产品支持、且受本次改动影响的平台指定浏览器；iOS 用 browser-ios（WebKit 内核 + iPhone 15 模拟），Android 用 browser-android（Chrome 内核 + Pixel 7 模拟），都是无头、隔离的浏览器。产品同时支持两者且改动影响两端时默认都覆盖。需要在页面上手动登录一次后反复使用（包括验证码、SSO）时，为用例指定可见 Chrome（browser-chrome）。必须复用用户日常 Chrome 中已有的登录态时，指定你正在用的 Chrome（browser-user-chrome），使用前要单独征得用户同意。
   - 用例：每个用例写明用例名、对应的 AC 编号、设备、前置条件、操作步骤、预期结果（页面上可见的状态）、需要核对的埋点请求（事件名和关键属性）。
   - 通用检查（每个用例都会做，不用逐条写）：控制台没有报错、没有意料之外的失败请求、页面没有横向溢出、可点击元素尺寸符合要求。
   - 性能与弱网检查：按“覆盖策略”第 2 点判断是否需要。每项写明页面和操作、网络条件（如 Slow 3G、Fast 4G）和 CPU 降速倍数、关注的现象、关注的指标（LCP、INP、CLS，不降速时的参考值为 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1）、是否做 Lighthouse 可访问性检查、是否检查内存泄漏。开发服务器上测得的指标只看相对变化。
5. 检查命令：列出要执行的完整命令（包括单次运行写法），只能基于 package.json 中已有的脚本。会修改文件或无法单次运行的脚本不列入，在第六步报告中说明。E2E 命令写在浏览器功能测试中。
6. 手工测试步骤：只列自动化测试覆盖不到的部分（真机 iOS Safari、App 内嵌 WebView、JSBridge、软键盘遮挡、刘海屏安全区、真实支付等），编号列出操作步骤和预期现象。
7. 覆盖清单：用表格列出每条 AC 的验证方式、相关场景和目标设备；未覆盖的高风险维度写原因和替代验证。普通风险或不适用的维度无需穷举所有组合。

写完后输出一段简短摘要：测试环境（本地或测试服地址、部署版本）、每层的用例数、设备、检查命令（`--only=browser` 时写“只做浏览器测试”）、是否做性能与弱网检查，以及能预见的需要用户协助的事项（启动本地页面的命令和地址、测试账号或 token、在可见 Chrome 中登录、使用你正在用的 Chrome 的同意等），说明用户可以现在就提供，也可以等到第四步。然后直接开始第三步（带 `--only=browser` 时直接开始第四步），不需要等待批准。

## 保存测试方案文件

将测试方案写入 `docs/plans/YYYYMMDD-test-简短英文名.md`（日期为当天，英文名用小写和连字符）。目录不存在就创建；同名文件已存在且不是本次的测试方案时，在文件名末尾加 `-2`、`-3`，不要覆盖。

写入前，先判断文件会不会被提交进仓库（以下 git 命令都是只读的）：
1. 运行 `git rev-parse --is-inside-work-tree`。失败说明不是 git 仓库：跳过本判断，在输出中注明。
2. 运行 `git ls-files -- docs/plans/`。有输出说明该目录已有文件被仓库跟踪：不要修改 git 配置，也不要执行 git rm，按“需要用户协助时”停下来告诉用户“docs/plans/ 已被仓库跟踪”，由用户决定是否继续写入。
3. 运行 `git check-ignore -q docs/plans/<文件名>.md`（文件还不存在也可以判断）：
   - 退出码 0：已被忽略，直接写入。
   - 退出码 1：未被忽略。运行 `git rev-parse --show-prefix` 和 `git rev-parse --git-path info/exclude`，用文件编辑工具（不用 echo 等终端命令）在 exclude 文件末尾追加一行 `/<前缀>docs/plans/`：前缀为空时就是 `/docs/plans/`；文件不存在就新建；已有相同的行就不追加；不改动原有内容。然后再运行一次 check-ignore，确认退出码为 0，并在输出中说明“已在本机 git exclude 中忽略 docs/plans/，只影响本机，不修改 .gitignore”。

文件开头写明 `状态：测试中` 和 `类型：测试`（测试完成后改为 `状态：已完成`）。文件必须包含以下章节，供子代理读取：

- 状态和类型
- 需求原文（输入是方案文件时，写明来源路径）
- 验收标准（AC 编号）
- 待确认事项与假设（Q 编号）
- 被测代码（文件:行号和证据等级）
- 测试现状
- 测试方案：测试分层、单元测试、集成或组件测试、浏览器功能测试（方式、环境、设备与浏览器服务、用例、性能与弱网检查）、检查命令、手工测试步骤
- 覆盖清单
- 测试基准：提交号和测试时未提交的改动（没有就写“无”）
- 测试环境：本地或测试服；测试服模式下写明测试服地址、部署版本及查询方式、版本对齐结论（一致 / 不一致 / 无法确定，以及用户的选择）、测试数据前缀、需要用户确认的沙箱情况

## 第三步：单元测试与检查命令（req-test-runner 子代理）

带 `--only=browser` 时跳过本步，在报告中写明。

1. 调用 req-test-runner。单元测试为“不适用”时，模式为“仅运行”；否则为“编写并运行”。调用时提供：
   - 测试方案文件路径；实现基准为测试基准的提交号；实现前已有改动为“无”。
   - 说明这是“只测试”的任务：没有修改业务代码，被测代码为测试方案“被测代码”中列出的文件，工作区中未提交的改动也属于被测代码；测试要按验收标准写，“业务代码问题”就是要找的缺陷，照常归因，不要为迁就现有行为修改断言。
2. 阅读测试报告，按归因处理：
   - 业务代码问题：记为“候选缺陷”。自己阅读相关代码和测试核实：测试是否确实按 AC 写，代码是否确实不符合 AC。确认后记入缺陷清单，写明失败的测试用例、断言的期望值与实际值、代码位置和证据等级。核实发现是测试写错时，再次调用 req-test-runner 并说明理由，由它修正。不要修改业务代码。
   - 测试代码问题：req-test-runner 应已自行修正；无法修正时，判断原因，需要调整测试方案的，更新测试方案文件后重新调用。
   - 原本就失败：与本需求无关的已有失败项，记入报告，不处理。
   - 不确定：自己核实；仍无法判断的，记为“疑似缺陷”，写明两种可能。
   - 需要用户协助：按“需要用户协助时”处理。
   - 它提出需要决定的事项（如需要新增依赖、方案中的用例无法实现）：涉及新增依赖或修改配置的，按“需要用户协助时”请用户决定；用例无法实现的，调整测试方案（换到其他层验证），不要直接删掉。
3. 不得要求 req-test-runner 删除用例、跳过用例、放宽断言或为掩盖问题更新快照。
4. 第三步完成的标准：req-test-runner 最后一次调用中完整运行了全部检查命令，每条命令都有明确结果；没有“待协助”的命令和用例；所有失败都已归因（缺陷、疑似缺陷或原本就失败）。

## 第四步：浏览器功能测试（req-browser-tester 子代理）

浏览器功能测试为“不适用”时跳过本步，在报告中写明原因。否则：

1. 本地模式：请用户按测试方案启动本地页面：给出启动命令和访问地址（需要构建后的预览页面时一并给出），然后停下，等用户确认已启动。用户告知的实际地址与方案不同时，以用户的为准，并更新测试方案文件。测试服模式跳过这一点（环境检查已经做过）。
2. 登录方式需要测试账号或 token、而用户还没有提供时，一并索取。
3. 有用例使用 browser-user-chrome 时，一并征求用户同意：说明将在用户日常使用的 Chrome 中操作哪个访问地址、执行哪些用例、会用到用户已有的登录态，并提醒用户确认 Chrome 正在运行、已安装 Playwright Extension，连接时在扩展的授权页中选择一个标签页。同意只在本次 /req-test 中有效。
4. 有用例使用 browser-chrome 时，告诉用户测试时会打开一个 Chrome 窗口，测试过程中不要在该窗口里操作。
5. 上面 1～4 点需要用户做的事，合在一条请求里一次提出，然后停下。
6. 调用 req-browser-tester，模式为“执行”。调用时提供：测试方案文件路径、实现基准（测试基准的提交号）、访问地址、登录方式及用户提供的登录信息、用户是否已同意使用 browser-user-chrome（用到时）、要执行的用例（方案中的全部浏览器用例和性能与弱网检查）；测试服模式下还要提供：“测试环境：测试服”、部署版本的查询方式、测试数据前缀、用户已确认为沙箱的操作；并说明这是“只测试”的任务：本次修改的业务文件为“无（只测试现有代码）”，被测代码见测试方案；页面行为与预期不符就是要找的缺陷，照常归因为业务代码问题。
7. 阅读浏览器测试报告，按归因处理：
   - 业务代码问题，以及“不稳定”的用例：记为“候选缺陷”，留到第五步确认。
   - 需要用户协助：按“需要用户协助时”处理。
   - 用例问题（步骤或预期写得不清楚、与验收标准矛盾）：修正测试方案文件中的用例，然后以“重新运行”模式重跑这些用例。修正会改变验收标准含义的，按“需要用户协助时”请用户确认。只能在真机上验证的，转到手工测试步骤，在报告中说明原因。
   - E2E 脚本本身写错：req-browser-tester 应已自行修正；无法修正时判断原因，必要时调整测试方案后重跑。
   - 原本就存在的问题（与本需求无关的页面报错或失败请求）：记入报告，不处理。
   - 归因为“不确定”或你对归因有疑问时，自己阅读相关代码和截图等证据核实。
8. 不得要求 req-browser-tester 跳过用例、放宽预期或修改断言。
9. 第四步完成的标准：没有“待协助”的用例；方案中的每个浏览器用例在每个指定设备上都有最后结果（通过、失败、不稳定，或经用户决定的未执行、转真机验证）；性能与弱网检查（有的话）都有结论。

## 第五步：确认缺陷

1. 合并候选缺陷：同一个现象、同一个根因在多个用例或设备上出现的，合并为一个缺陷，列出全部受影响的用例和设备。
2. 复现确认：把来自浏览器测试的每个候选缺陷，以及第三步中能在页面上表现出来的缺陷，整理成从全新状态开始的复现步骤（打开哪个地址、点击什么、输入什么、需要模拟什么接口返回），写明实际结果和期望结果。全部缺陷合在一次调用中，调用 req-browser-tester，模式为“复现”，提供访问地址、每个缺陷的复现步骤、设备与浏览器服务、登录方式和登录信息（测试服模式下同样提供第四步第 6 点中的测试服信息），要求每个缺陷在受影响的每个设备上都尝试复现。
3. 按复现结果确定每个缺陷的状态：
   - 已确认：按复现步骤能稳定出现。
   - 偶现：多次尝试中只有部分出现，写明尝试次数和出现次数。
   - 未能复现：按步骤没有出现。保留为“疑似缺陷”，附上原测试中的证据和尝试过的条件，不要直接删掉。
   复现结果说明步骤写得不对（例如漏了前置条件）时，修正步骤后再复现一次。
4. 定位疑似代码位置：阅读代码，写出最可能出问题的位置（文件:行号）和理由，标注证据等级。只定位，不修复。
5. 严重程度：
   - 致命：主流程无法完成、数据错误或丢失、安全问题、页面崩溃或白屏。
   - 严重：主要功能结果不符合验收标准，没有可行的绕过办法。
   - 一般：次要功能或异常路径不符合预期，或者有绕过办法。
   - 轻微：文案、样式、对齐等不影响功能的问题。
6. 依赖假设的缺陷：标注对应的 Q 编号，说明假设不成立时这条是否还算缺陷。

## 第六步：测试报告

在对话中输出以下内容，并追加到测试方案文件末尾的“## 测试报告”章节，然后把文件开头的状态改为 `状态：已完成`：

1. 结论摘要：测试范围；测试环境（本地或测试服地址、部署版本）；测试基准；每层用例的通过、失败、不稳定、未执行数量；缺陷数量（按严重程度分）；一句话总体结论。
2. 缺陷清单：按严重程度从高到低排列，每个缺陷编号为 B1、B2……，逐个写明：
   - 标题：一句话说清在什么情况下出了什么问题。
   - 严重程度、状态（已确认 / 偶现 / 疑似）、对应的 AC 编号，依赖假设时注明 Q 编号。
   - 环境：设备与浏览器服务、访问地址、测试基准、登录状态（只写账号类型，不写账号本身）、需要模拟的接口返回。测试服模式下还要写：部署版本、发生时间、用到的测试数据（如订单号）、失败请求的 trace ID 或 request-id（响应头或返回内容中有时），方便后端查日志。
   - 前置条件。
   - 复现步骤：编号列出，从打开页面开始，具体到点击哪个元素、输入什么内容。来自单元测试的缺陷，写明运行哪个测试文件的哪个用例（完整命令）。
   - 实际结果和期望结果：期望结果引用 AC 或需求原文。
   - 复现频率：例如“3/3 次”“2/5 次”。
   - 证据：截图路径、控制台报错、失败请求（地址、状态码、返回摘要，登录凭证用“***”代替）、失败的测试用例及断言的期望值与实际值。
   - 疑似代码位置（文件:行号）及证据等级。
   - 修复入口：一条可以直接粘贴的 `/req-bugfix <问题描述>` 消息，包含复现步骤、期望结果、实际结果、环境，以及本测试报告的路径和缺陷编号。有能抓住这个缺陷的失败测试时，在消息末尾加一行：“已有失败的回归测试：<测试文件路径> 中的用例 <用例名>，运行命令 <单次运行的完整命令>，当前失败摘要：<断言的期望值与实际值>”，供 /req-bugfix 直接沿用。
   没有发现缺陷时写“未发现缺陷”，并说明覆盖了哪些场景。
3. 用例执行结果：每个用例在每个设备上的最后结果，以及对应的证据。
4. 检查命令结果：每条命令及结果，附关键输出摘要；没能作为检查命令的脚本及原因。
5. 通用检查、埋点核对、性能与弱网检查的结论（注明是在开发服务器还是构建后的预览上测得）。
6. 覆盖情况：每条 AC 对应的单元、组件、浏览器用例和结论；所选测试维度及未覆盖的高风险维度、原因和替代验证。
7. 未执行和无法自动化的项：“未执行（用户决定）”“转真机验证”的用例及原因；可以直接交给测试同学使用的手工测试步骤（环境、数据准备、操作步骤、预期结果）。
8. 协助请求记录：过程中发出的协助请求（H 编号）及处理结果。
   测试服模式下，在这里之后加上：开始和结束时的部署版本（不一致时说明影响了哪些用例）；版本对齐结论；本次测试在测试服上创建的数据清单（类型、名称或 ID、所在页面），供用户清理。
9. 新增的测试文件：逐个列出，并标出哪些用例对应哪个缺陷。说明发现缺陷的那些测试在缺陷修复前会一直失败；用 /req-bugfix 修复时会被直接沿用为“修复前必须失败”的回归测试，修复后应当通过。这些文件还没有提交，在新的 worktree 中修复时不会自动带过去（届时会按用例描述重新编写）。是否保留由用户决定，不要自行删除。
10. 原本就存在的问题：与本需求无关的失败测试、页面报错和失败请求（没有就写“无”）。
11. 测试局限：模拟环境与真机的差异、依赖假设的部分、没有覆盖的场景及原因。

不要自动提交（git commit）或推送，除非用户明确要求。

结束时说明：“测试已完成，发现 N 个缺陷（致命 a、严重 b、一般 c、轻微 d），报告已追加到 <测试方案文件路径>。需要修复时，可以把缺陷清单中的 /req-bugfix 消息粘贴到新会话中执行。”
