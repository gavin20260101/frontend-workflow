# 按方案实现、测试与审核

用户调用本命令时附带的参数，是 `/req-analysis` 生成的方案或已批准的 Superpowers 实施计划路径。用户运行本命令即表示已批准该计划。

分工：你负责协调整个流程；业务代码由你或选定的 Superpowers 计划执行方式负责；req-test-runner 子代理负责实现前的单元与组件 RED 测试、测试修正和检查命令；已有 E2E 框架时，req-browser-tester 负责实现前的 E2E RED 测试和实现后的浏览器验证；req-code-reviewer 子代理负责前端专项只读审核。req-* 子代理都看不到本次对话，调用时必须把它们需要的信息写全。

如果 Superpowers 可用且输入是 Superpowers 计划，读取并执行 `superpowers:executing-plans`；多任务计划由用户选择子代理执行时，使用 `superpowers:subagent-driven-development`。在 Superpowers 模式中，逐任务遵循 `superpowers:test-driven-development`；遇到异常或测试失败时使用 `superpowers:systematic-debugging`，完成前使用 `superpowers:verification-before-completion`。没有 Superpowers 时，按本技能后文的同一 RED-GREEN 规则执行。

两套流程不能叠加执行。Superpowers 执行技能只负责任务的执行顺序、业务代码的实现方式、工作区和进度记录（包括它自带的脚本）。以下几件事以本技能为准，Superpowers 技能中与之不同的规定不采用：
- 测试由谁写、由谁验证：按第二步、第三步。
- 审核由谁做、做几次：按第五步。使用 `executing-plans` 时，不再另派它的全分支审核，由第五步的 req-code-reviewer 完整审核代替。使用 `subagent-driven-development` 时，它的逐任务审核和全分支审核照常进行，第五步改为前端专项审核。
- 修复后是否复审：按第五步第 7 点。
在第一步的执行确认中写明本次用哪个 Superpowers 执行技能，以及上面三件事各按哪一方执行。

下文的“项目规则”指项目中的 CLAUDE.md 和 CLAUDE.local.md（存在时）。

## 在 worktree 中执行时

运行 `git rev-parse --git-dir` 和 `git rev-parse --git-common-dir`，两者不同说明当前在 worktree 中（例如由 /req-parallel 安排的并行任务）。这时：
- 方案文件必须能从本 worktree 的路径读取。Superpowers 计划通常位于 `docs/superpowers/plans/`，独立方案位于 `docs/plans/`。路径不存在时，提醒用户在创建计划的会话或正确 worktree 中运行本命令。
- worktree 根目录下没有 node_modules 时，给出 `cd <worktree 路径>` 和包管理器的安装命令（如 `pnpm install`），请用户在终端执行后回复，然后停下。不要自己安装。
- 访问地址优先使用方案中记录的本 worktree 地址；用户告知的实际地址不同时，以用户的为准，并更新方案文件。
- 结束时按第六步末尾的“worktree 收尾”说明。

## 需要用户协助时（适用于每一步）

任何一步需要用户本人处理时，立即停下来向用户发出请求。包括你自己遇到的情况，也包括子代理报告中“需要用户协助”不是“无”的情况。不要跳过，不要等后面的步骤做完再一起问，也不要把受影响的用例或命令记为“未执行”或“通过”写进报告。

1. 发出请求：标题写“需要你协助（第 N 步，来自 <主代理 / 子代理名>）”，按 H 编号逐条列出：看到的情况（有截图时附路径）；需要用户做什么（具体到命令、地址、窗口、按钮）；做完后回复什么；影响哪些用例或命令。同时有多条时一次列全。最后说明用户处理完后会接着做什么。
2. 发出请求后停下，等用户回复。
3. 用户回复后，以“继续”模式调用同一个子代理。调用时附上：原来的调用模式和全部原有输入；每条 H 的处理结果；上一次报告中已有结果的用例和命令。用户提供的登录信息只在调用子代理时传入，不写入方案文件、代码、报告或其他任何文件。用户的处理涉及偏离方案（例如改用可见 Chrome 执行某些用例），按第二步第 3 点同步更新方案文件。
4. 只有用户本人明确表示某项不处理（例如“跳过”“转手工”“转真机”）时，才能把相关用例记为“未执行（用户决定：……）”或“转真机验证”，并转到第六步的手工测试步骤。
5. 你自己的工具调用被权限确认拒绝时，同样按本节处理：说明被拒的工具和用途，询问用户是放行还是换一种做法。需要反复使用的，可以提示用户在项目的 `.claude/settings.json` 的 `permissions.allow` 中加入对应规则。

## 第一步：读取并检查方案

1. 没有提供路径时，列出 `docs/plans/` 与 `docs/superpowers/plans/` 下最近的几个方案文件，请用户指定，然后停下。
2. 读取计划并识别格式：
   - 独立方案：按既有要求检查状态、验收标准、待确认事项及答复、风险等级、修改文件、测试方案、检查命令和回滚方式；缺陷修复方案还要包含复现结论、根因和回归测试。
   - Superpowers 计划：检查任务清单、每项的文件和验证步骤，以及 `Frontend quality supplement (req-workflow)` 章节。缺少前端补充时，先停下来，请用户运行 `/req-analysis <计划路径>` 后再执行。已批准的计划应由用户在调用本命令前确认。
   - 旧版方案没有“浏览器功能测试”时，按“不适用”处理，并在执行确认中说明。
3. 以下情况必须停下来提示，不要自行补写方案后直接开始改代码：
   - 文件不存在，或独立方案缺少必需章节，或 Superpowers 计划缺少任务、验证步骤或前端补充；
   - 独立方案状态为“含待确认项”；
   - 独立方案的待确认事项中有既不是“已答复”、也不是“按假设处理”的条目；
   - 独立方案没有具体测试用例或“不适用”原因；Superpowers 计划的前端补充没有把 AC 映射到验证方式；
   - 缺陷修复方案的复现结论为“未复现”，且根因没有 A 级证据。
   Superpowers 计划由用户在调用本命令前确认批准；其设计文档中的未决问题仍需先解决。独立方案中标注为“按假设处理”的条目可以继续实现，但要在执行确认中列出这些假设。
4. 检查代码是否已偏离方案：独立方案或 Superpowers 计划有记录代码基准时，对比该提交号与当前代码（如 `git diff <提交号> --stat -- <计划涉及文件>`）。如果计划没有记录基准，跳过偏离检查，在下一步以当前 `HEAD` 作为实现基准，并把未提交代码改动列为实现前已有改动。
5. 确定实现基准：
   - 方案文件中已经有“实现基准”记录时，说明之前开始过实现：不要覆盖，停下来询问用户是沿用原基准继续，还是重新开始。
   - 运行 `git status --porcelain`。独立模式排除 `docs/plans/` 和 `.claude/worktrees/`；Superpowers 模式只排除当前计划文件和 `.claude/worktrees/`。其他改动或未跟踪文件需列出，请用户先提交或暂存，或者明确回复“带着这些改动继续”。选择继续时，把这些文件记为“实现前已有改动”。
   - 运行 `git rev-parse HEAD`，把完整提交号记为“实现基准”。用文件编辑工具在方案文件末尾追加 `## 实现记录` 章节，写明实现基准和实现前已有改动的文件（没有就写“无”）。
   - 之后传给子代理的基准一律是实现基准。方案中记录的提交号只用于上面第 4 点的偏离检查。
   - 不是 git 仓库时，实现基准记为“无”，子代理改为根据你提供的改动文件清单逐个阅读全文。
6. 把方案“修改的文件”逐个与项目规则中的高风险区域清单匹配，记下命中的文件。项目规则中没有清单、清单为空或仍是待填写状态时，记为“项目未配置高风险区域”。
7. 输出简短的执行确认：计划任务和文件、高风险区域、实现前测试、检查命令、浏览器验证方式与设备、执行代理、审核方式（完整审核或前端专项审核，见第五步），以及预期的用户协助。用 Superpowers 子代理执行时说明由其按任务实现和评审，最后的 req-code-reviewer 只审前端 AC、设备行为、埋点与浏览器证据。调用本命令表示计划已批准；不再重复审批。
   命中高风险区域的文件，在执行确认中逐个写明改动要点，请用户一次确认。用户确认后，实现中按这些要点修改不再逐个文件停下；超出这些要点的改动按第二步第 3 点处理。
   计划中有会在实现时让你停下来问用户的事项（例如计划步骤与项目规则冲突、规则或配置范围需要扩大），也在这里一并列出，不要等到做到那个任务时再单独问。

## 第二步：实现

### 实现前测试（所有行为改动）

每个会改变行为的任务，在修改对应业务代码前先完成计划中适用的 RED 阶段。单元或组件用例由 `req-test-runner` 负责；已有 E2E 框架且计划选择 E2E 脚本时，由 `req-browser-tester` 负责 E2E 用例。两层都在计划中时，两者都要先验证失败。若只有浏览器手工验证，或测试框架不适用、无法自动验证，沿用已批准计划中的原因和手工步骤；不要为此自行新增依赖。

1. 按计划中的当前任务调用 `req-test-runner`，模式为“编写并验证失败（RED）”，传入该任务的 AC、单元/组件用例、文件、实现基准和实现前已有改动。只有浏览器手工验证时跳过此代理。多任务计划逐任务执行，后续任务等它依赖的接口确定后再写测试。
   调用前先写一份任务简报，把简报路径传给它。简报写入本机不提交的目录：Superpowers 模式用执行技能的工作区，独立模式用 `docs/plans/briefs/<方案文件名>/`。简报的内容：
   - 该任务在计划中的原文（任务段落和对应的前端补充条目）；
   - 与该任务有关、已经定下的决策（用户的答复、执行确认中的约定、前面任务记下的裁决）；
   - 前面任务已经新增或修改的测试文件，以及每个文件的要点；
   - 要运行的测试命令。
   简报要写全到子代理不需要通读整份计划就能工作。
2. 计划选择 E2E 脚本时，在同一任务的业务代码修改前调用 `req-browser-tester`，模式为“编写并验证失败（RED）”，传入 AC、E2E 文件路径、单次运行命令、访问地址、环境、设备和登录方式。若本地页面需要手动启动，先请用户按计划启动并确认；若测试脚本由现有 Playwright 配置启动页面，则按该脚本运行。RED 阶段只运行当前目标用例，不做全量浏览器检查。
3. 每条 RED 用例必须因行为断言得到与计划一致的失败，而不是语法、导入、mock 或环境错误。测试错误由负责的子代理修正后重跑；无法修正时停下来。手工浏览器验证不强求制造 RED，按计划保留实现前后的对照步骤。
4. 测试在实现前意外通过时停下来，检查是否覆盖尚未实现的行为；不得通过放宽断言或改动业务代码来制造失败。
5. 记录测试文件、每条用例的失败摘要和运行命令到计划的实现记录。缺陷修复还需记录复现截图；若方案没有“已复现”结论，或基准代码已经变化且涉及页面，先调用浏览器子代理重新复现。
   收到 RED 报告后，由你用 `cp` 把本次 RED 的测试文件复制一份，保存到简报所在目录下的 `red/<任务编号>/`（保持相对路径），作为 GREEN 阶段核对断言没被改动的依据。不要让测试子代理做这一步：钩子不允许它用 `cp`。
6. 在 Superpowers 模式中，完成适用的 RED 阶段后再执行该任务的 Superpowers 计划步骤，并遵循 `superpowers:test-driven-development` 的 RED-GREEN-REFACTOR 循环。没有 Superpowers 时也遵循同一循环。

### 修改业务代码

如果可以使用 karpathy-guidelines 技能（由 andrej-karpathy-skills 插件提供），先加载它；Superpowers 可用时，遵循其 TDD 与计划执行规则。方案已经过用户批准，原则中“有疑问先问”的部分只针对方案没有覆盖的新疑问。
1. 只修改方案中列出的业务文件。测试文件由 req-test-runner 和 req-browser-tester 负责，你不修改。
2. 不做方案“不做什么”中排除的内容，也不顺手做“可选的局部整理与技术债”中的项目。
3. 实现过程中如果发现方案需要调整（要多改文件、接口要变、需要新增依赖、触及高风险区域等），先停下来说明原因和建议的调整，得到确认后再继续，并同步更新方案文件。
4. 对第一步第 6 点中命中高风险区域的文件，按第一步第 7 点在执行确认中一次确认。改动超出确认过的要点时，在修改该文件前停下来：说明具体改动，等用户确认后再改。
5. 使用第三方库的 API 或配置项、拿不准用法或版本差异时，如果可以使用插件自带的 Context7 服务，先按项目 package.json 中的版本查询文档；查询内容只写库名、版本和通用的技术问题，不写业务代码、内部接口地址、业务名称或账号信息。查不到时不要凭记忆硬写，在最终报告的遗留问题中注明。
6. 每个任务先完成 RED 测试，再做最小实现并运行同一测试确认 GREEN；需要整理代码时再做 refactor，并再次运行测试。多任务执行中，每个 Superpowers implementer 都要收到该任务的 RED 结果和测试文件路径。测试失败或计划步骤与代码不符时，使用 `superpowers:systematic-debugging`（可用时）找根因，再更新计划中的执行记录。

## 第三步：单元测试与检查命令（req-test-runner 子代理）

1. 每个任务完成后，由你自己确认 GREEN：
   - 运行该任务 RED 阶段的同一批目标测试，确认全部通过；
   - 用 `diff -r` 对照 `red/<任务编号>/` 中的快照，确认测试文件没有被改动。有改动时停下来查原因：测试写错的，交 req-test-runner 修正并说明理由，不要自己改测试。
   该任务有 E2E RED 用例时，再调用 `req-browser-tester`“重新运行”，传入对应用例和失败结果。
   全部任务完成后再调用 `req-test-runner`“完整检查”，运行所有单元/组件测试和检查命令。调用前你已经在当前代码上运行过、之后又没有改动的命令，不要另派子代理重跑；完整检查只运行一次。若单元/组件测试没有可用框架且计划明确“不适用”，`req-test-runner` 的完整检查阶段改用“仅运行”；计划中的 E2E 验证仍按浏览器测试流程执行。不得在本阶段首次编写计划内测试；缺陷回归测试的断言和预期值不得修改。
2. 阅读它返回的测试报告，按归因处理：
   - 业务代码问题：使用 Superpowers systematic debugging（可用时）或同等根因分析修复，然后自己重跑相关测试；全部修完后调用一次 req-test-runner“重新运行”。
   - 测试代码问题：req-test-runner 应已自行修正。如果它报告无法修正，判断原因；需要偏离方案时，按第二步第 3 点停下来说明。
   - 原本就失败：不修，记入最终报告。
   - 归因为“不确定”或你对归因有疑问时，自己阅读相关代码和测试核实，不要直接采信。确认是测试写错时，再次调用 req-test-runner 并说明理由，由它修正。
   - 它提出需要你决定的事项（如新增依赖、方案中的用例无法实现）：按第二步第 3 点停下来请示。
   - 需要用户协助：按“需要用户协助时”处理。
3. 你不得要求 req-test-runner 删除用例、跳过用例、放宽断言或为掩盖问题更新快照。缺陷修复方案的回归测试在修复后仍失败时，要修的是业务代码；确认是测试本身写错时，停下来说明，经用户同意后才能修改它的断言或预期值。
4. 同一个问题经过 3 次修复（包括你修业务代码和 req-test-runner 修测试）仍然失败，停下来，报告失败原因和已尝试的做法，等待指示。
5. 第三步完成的标准：req-test-runner 最后一次调用中完整运行了全部检查命令，除“原本就失败”的条目外全部通过。以这次结果为准。因超时或输出不完整而记为“不确定”的命令，以及“待协助”的命令和用例，都不算通过：先核实原因，需要用户处理时按“需要用户协助时”处理。

## 第四步：浏览器功能测试（req-browser-tester 子代理）

方案的浏览器功能测试为“不适用”时跳过本步，在报告中写明原因。已有 E2E 框架并选择脚本时，RED 测试在第二步实现前完成；本步在第三步完成后执行浏览器验证：

1. 如实现前 RED 阶段已要求本地页面，沿用用户已启动的页面和实际地址；否则请用户按方案启动本地页面，给出启动命令和访问地址（方案的性能检查要求使用构建后的预览页面时，一并给出预览的启动命令和地址），然后停下，等用户确认已启动。用户告知的实际地址（例如端口被占用后自动换了端口）与方案不同时，以用户的为准，并更新方案文件。不要自己启动 dev server 或其他常驻进程。
2. 方案的登录方式需要测试账号或 token、而用户还没有提供时，向用户索取。只在调用子代理时传入，不写入方案文件、代码、报告或其他任何文件。
3. 方案中有用例使用“你正在用的 Chrome”（browser-user-chrome）时，先停下来征求用户同意：说明将在用户日常使用的 Chrome 中操作哪个访问地址、执行哪些用例、会用到用户已有的登录态，并提醒用户确认 Chrome 正在运行、已安装 Playwright Extension，连接时需要在扩展的授权页中选择一个标签页。用户明确同意后才能使用，同意只在本次 /req-implement 中有效（包括第四步和第五步中的重跑）；用户不同意时，这些用例记为“未执行（未获用户同意）”，转到手工测试。
4. 方案中有用例使用“可见 Chrome”（browser-chrome）时，告诉用户测试时会打开一个 Chrome 窗口，测试过程中不要在该窗口里操作；第一次需要登录时，子代理会停下来，请用户在该窗口中登录。
5. 调用 req-browser-tester，模式为“执行”。调用时提供：方案文件路径、实现基准、访问地址、登录方式及用户提供的登录信息、用户是否已同意使用 browser-user-chrome（用到时）、本次修改的业务文件及每个文件的改动要点、要执行的用例（默认为方案中的全部浏览器用例）。
6. 阅读它返回的浏览器测试报告，按归因处理：
   - 业务代码问题：由你修复业务代码，先调用 req-test-runner“重新运行”，确认单元测试和检查命令仍然通过；再调用 req-browser-tester，模式为“重新运行”，附上修复说明，重跑失败的用例和与修复相关的用例。
   - 需要用户协助（页面打不开、浏览器未安装、需要登录或登录失效、验证码或 SSO 等需要本人操作的页面、browser-user-chrome 未获同意或连接失败、测试数据缺失、后端接口异常、工具调用被拒等）：按“需要用户协助时”处理（浏览器未安装时，给出报告中的安装命令）。不要自己安装浏览器或依赖。
   - 用例问题（方案中的步骤或预期不清楚、与验收标准矛盾、在模拟环境中无法执行）：按第二步第 3 点停下来说明，经用户确认后更新方案。只能在真机上验证的，经用户同意后转到手工测试步骤。
   - E2E 脚本本身写错：req-browser-tester 应已自行修正；无法修正时判断原因，必要时按第二步第 3 点停下来。
   - 原本就存在的问题（与本次改动无关的页面报错或失败请求）：不修，记入最终报告。
   - 归因为“不确定”、“不稳定”或你对归因有疑问时，自己阅读相关代码和截图等证据核实，不要直接采信。
7. 你不得要求 req-browser-tester 跳过用例、放宽预期或修改断言来通过测试。
8. 同一个问题经过 3 次修复仍然失败，停下来，报告失败原因和已尝试的做法，等待指示。
9. 第四步完成的标准：没有“待协助”的用例；方案中的每个浏览器用例，在指定的每个设备上，最后一次结果都是“通过”；或经用户同意记为“转真机验证”；或因用户不同意使用 browser-user-chrome 记为“未执行（未获用户同意）”、因用户明确决定不处理记为“未执行（用户决定：……）”，并已转到手工测试。

## 第五步：独立代码审核

第四步完成后（或第四步不适用时，第三步完成后），调用 req-code-reviewer 子代理审核本次改动。只派这一个审核员，不另派全分支审核。审核范围：
- 完整审核：独立模式，以及用 `executing-plans` 执行的 Superpowers 计划。计划改动了页面或交互时，同一次审核里一并检查前端专项内容；没有改动页面或交互时，传入“本次不涉及页面，前端专项不适用”。
- 前端专项审核：用 `subagent-driven-development` 执行、Superpowers 已做过逐任务审核和全分支审核时，明确传入“仅做前端专项审核：AC 对照、响应式与可访问行为、埋点、浏览器证据和手工测试缺口；不重复一般代码质量审核”。这种情况下计划没有改动页面或交互时，跳过本步，在报告中写明原因。

0. 专项检查（只在第 1 轮审核前做一次）：独立模式下，风险等级为 L2 及以上、且可用代理中有 `pr-review-toolkit:silent-failure-hunter` 和 `pr-review-toolkit:pr-test-analyzer` 时，同时调用这两个代理。Superpowers 已做任务级和全分支审核时跳过这一步，避免重复；在最终报告中说明。
   - silent-failure-hunter：检查被吞掉的错误、空的 catch、缺失的错误处理和失败提示、不恰当的兜底逻辑。
   - pr-test-analyzer：检查测试是否覆盖了关键行为和异常路径，按 1～10 标出缺口的严重程度。
   - 调用时提供：实现基准、本次改动的文件清单（只看这些文件在 `git diff <实现基准>` 中的改动和未跟踪的新文件）、方案文件路径；并说明“只读，不修改任何文件，不运行测试，只输出发现的问题及文件和行号”。
   - 它们的结果不直接作为修改依据，原样作为“专项检查参考意见”交给 req-code-reviewer 复核。
   - 风险等级为 L1，或没有安装 pr-review-toolkit 时跳过，在最终报告中写明原因。
1. 调用时提供：方案文件路径、实现基准、实现前已有改动的文件、本次改动的文件清单（你修改的业务文件，加上 req-test-runner 和 req-browser-tester 报告中新增或修改的测试文件）、命中高风险区域的文件、浏览器测试结果摘要（每个用例在每个设备上的结论、通用检查、性能与弱网检查和埋点核对的结论、转真机验证的项）、审核轮次。第 1 轮还要附上专项检查参考意见（做过时）。第 2 轮起，附上上一轮的问题清单，以及每条的处理结果（已修复 / 暂不处理 + 理由 / 有异议 + 理由）。子代理看不到本次对话，它需要的信息必须在调用时写全。
2. 拿到审核报告后，开头有“需要用户协助”时，先按“需要用户协助时”处理，用户处理后重新审核本轮（不计入 3 轮上限）。然后逐条处理：
   - 阻断：必须处理，修复或提出异议。
   - 建议：在方案范围内且改动较小的，予以修复；否则记为“暂不处理”并写明理由。
   - 提示：不处理，原样记入报告。
   - 不认同的条目：标记为“有异议”并写明理由（引用代码、验收标准或方案内容作为依据）。不要为了通过审核而做不正确的修改。
   - 审核员对某条异议给出“维持”后，不要再次提出相同的异议：要么按审核意见修改，要么在结束时交给用户裁决。
3. 按问题所在位置分派修复：
   - 业务代码的问题：由你修复。
   - 单元测试或组件测试的问题：调用 req-test-runner，模式为“按审核意见修正”，附上对应的 R 编号和审核内容。
   - E2E 脚本或浏览器用例执行的问题：调用 req-browser-tester，模式为“按审核意见修正”，附上对应的 R 编号和审核内容。
4. 标注为“超出方案范围”的条目，或者修复需要多改文件、修改接口、新增依赖、触及高风险区域时，按第二步第 3 点处理：先停下来说明，得到确认后再继续，并同步更新方案文件。
5. 修复时遵守第二步至第四步的全部约束。尤其不允许为了通过审核或测试而删除用例、跳过用例、放宽断言。
6. 本轮有任何修复时：
   - 改了业务代码：自己先跑相关测试；全部修完后调用一次 req-test-runner“重新运行”；修复涉及页面表现或交互时，再调用 req-browser-tester“重新运行”相关的用例。
   - 改了测试：对应的子代理在“按审核意见修正”时已完整重跑；之后你没有再改业务代码的，不再另派“重新运行”。
   按第三步第 2～5 点和第四步第 6～9 点处理结果。
7. 是否进入下一轮审核：
   - 本轮有阻断项被修复，或有“有异议”的条目：进入下一轮。第 2 轮起，只复核上一轮的问题清单和修复涉及的文件，不重新审核全部改动；调用时传入“复核范围：上一轮问题及修复涉及的文件”和这些文件的清单。
   - 本轮只修了建议项、没有阻断项和异议：不再复审，以第 6 点的检查结果为准，在报告中列出这些修复。
8. 结束条件：
   - 审核结论为“通过”，或按第 7 点不再复审：进入第六步。
   - 已完成 3 轮审核，仍有未解决的阻断项：停下来，列出这些条目、审核员的意见、你的理由和建议，等待用户决定。

## 第六步：测试与审核报告

在对话中输出以下内容，并追加到当前计划文件末尾的“## 实现、测试与审核报告”章节：

1. 修改清单：实际修改的文件，以及与方案的差异（没有差异就写“无”）。缺陷修复方案在这里加上缺陷修复记录：根因；修复前的证据（回归测试的失败摘要、复现截图）；修复后的证据（同一批回归测试通过、复现步骤在浏览器中出现期望结果）；同一根因的其他影响点及处理情况。
2. 单元测试与检查命令结果：以 req-test-runner 最后一次完整运行为准，列出每条命令及结果（通过 / 失败数量），附上关键输出摘要；并说明调用 req-test-runner 的次数。
3. 浏览器功能测试结果：方式和设备；每个用例在每个设备上的最后结果；通用检查（控制台报错、失败请求、横向溢出、点击区域）和埋点核对的结论；性能与弱网检查的指标和现象（有的话，注明是在开发服务器还是构建后的预览上测得）；截图等证据的路径；“不稳定”“转真机验证”和“未执行（用户决定）”的用例；过程中发出过的协助请求及处理结果；调用 req-browser-tester 的次数。不适用时写明原因。
4. 代码审核记录：专项检查是否执行（未执行时写明原因）及其意见的采纳情况；审核轮数和最终结论；每条问题的编号、严重度和处理结果（已修复 / 暂不处理 + 理由 / 有异议 + 审核员最终结论）。“提示”级别的条目单独列出，供后续参考。
5. 用例与验收标准对照表：每条验收标准对应哪些单元测试、组件测试和浏览器用例，状态是“已自动化覆盖”“需手工验证”还是“未覆盖（附原因）”。
6. 待执行的手工测试步骤：可以直接交给测试同学使用，包含环境（真机型号、系统版本、App 版本）、数据准备、操作步骤、预期结果；包括转真机验证的项，以及浏览器模拟环境无法覆盖的检查点。
7. 回归测试清单：需要回归的功能点和场景。
8. 原本就失败的测试和原本就存在的问题：与本次改动无关的失败项和页面问题（没有就写“无”）。
9. 遗留问题与风险：未覆盖的部分、已知限制、建议后续补充的测试。如果有“按假设处理”的条目，逐条列出假设内容，以及假设不成立时需要修改的代码和测试。
10. 回滚方式：引用方案中的回滚方式，并补充本次实际改动需要注意的地方。
