# 按方案实现、测试与审核

用户调用本命令时附带的参数，是 `/req-analysis` 生成的方案或已批准的 Superpowers 实施计划路径。用户运行本命令即表示已批准该计划。

分工：你负责协调整个流程、写业务代码和运行完整检查；req-test-runner 子代理负责实现前的单元与组件 RED 测试、实现后补写的测试和测试修正；已有 E2E 框架时，req-browser-tester 负责实现前的 E2E RED 测试和实现后的浏览器验证；req-code-reviewer 子代理负责只读的完整审核。req-* 子代理都看不到本次对话，调用时必须把它们需要的信息写全。

只用本技能这一套流程。输入是 Superpowers 计划时，计划只作为任务清单和设计依据：不加载 `superpowers:executing-plans`、`superpowers:subagent-driven-development`、`superpowers:test-driven-development`、`superpowers:verification-before-completion`。用户调用本命令，即表示明确要求本次不使用这些技能。任务顺序、测试先行的范围、测试由谁写和验证、审核几轮，都按本技能。只有同一个问题修了一次仍失败、或根因不清时，才使用 `superpowers:systematic-debugging`（可用时）。karpathy-guidelines 不在排除之列：它只约束代码怎么写，不规定流程，在第二步“修改业务代码”前加载。

计划中逐行写好的代码只作参考：实现时以计划的文件、验收标准和“不做什么”为准，代码按当前仓库的实际情况写。计划头部的 REQUIRED SUB-SKILL 说明和各任务里的 `git commit` 步骤都不执行：执行方式以本技能为准，提交只在第六步用户要求时进行。实现和审核过程中，也不要主动调用 `pr-review-toolkit:code-simplifier` 这类会改代码的代理，否则会改动审核员已经审过的代码。

下文的“项目规则”指项目自己的指令文件：`CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/` 下的文件和项目根目录的 `AGENTS.md`，存在的都算。已经在你上下文里的不用重复读取；没有被自动加载的（常见于同时有 `CLAUDE.md` 和 `AGENTS.md` 的项目里的 `AGENTS.md`），用 Read 读一遍。

## 上下文被压缩之后

这个流程很长，中途上下文几乎一定会被压缩。压缩后本技能只保留开头的一部分，读过的规则文件也不再保留。发现自己看到的是之前对话的摘要、而不是原文时，先做下面几件事再继续，不要凭摘要往下做：

1. 用 Read 重新读取 `${CLAUDE_SKILL_DIR}/SKILL.md` 全文，以及 `${CLAUDE_PLUGIN_ROOT}/references/test-first-scope.md`。
2. 本次运行带 `--auto` 时，重新读取 `${CLAUDE_PLUGIN_ROOT}/references/unattended-mode.md`。
3. 读取方案文件“实现记录”里的“进度”小节，从记录的位置接着做；无人值守运行时自己启动的后台进程也记在那里。
4. 可用技能中有 karpathy-guidelines 时，重新加载它（见第二步“修改业务代码”）。

有人值守时，接着做的同时在下一条消息里提一句：上文已经压缩过、仍然很长，可以新开会话（在 worktree 中改为 `/clear`）运行同一条 `/req-implement <方案路径>`，按“进度”小节接着做，后面每一步的用量会小很多。只是提示，不停下等回复。

## 无人值守模式（`--auto`）

参数开头的选项中带 `--auto` 时，本次是无人值守运行，没有人能回复。先读取 `${CLAUDE_PLUGIN_ROOT}/references/unattended-mode.md`：下文所有“停下来”“等用户回复或确认”“请用户……”的地方都按它处理，不提问、不等待，并按它的要求写“无人值守记录”和结束块。`--auto` 可以和其他选项以任意顺序出现，先去掉它，再按下文解析其余参数。

不带 `--auto` 时，本节和该文件都不适用，下文的每一处停顿都照原样停下等用户。

## 在 worktree 中执行时

运行 `git rev-parse --git-dir` 和 `git rev-parse --git-common-dir`，两者不同说明当前在 worktree 中（例如由 /req-parallel 安排的并行任务）。这时：
- 方案文件必须能从本 worktree 的路径读取。Superpowers 计划通常位于 `docs/superpowers/plans/`，独立方案位于 `docs/plans/`。路径不存在时，提醒用户在创建计划的会话或正确 worktree 中运行本命令。
- worktree 根目录下没有 node_modules 时，给出 `cd <worktree 路径>` 和包管理器的安装命令（如 `pnpm install`），请用户在终端执行后回复，然后停下。不要自己安装。
- 访问地址优先使用方案中记录的本 worktree 地址；用户告知的实际地址不同时，以用户的为准，并更新方案文件。
- 结束时按第六步末尾的“worktree 收尾”说明。

## 需要用户协助时（适用于每一步）

任何一步需要用户本人处理时，立即停下来向用户发出请求。包括你自己遇到的情况，也包括子代理报告中“需要用户协助”不是“无”的情况。不要跳过，不要等后面的步骤做完再一起问，也不要把受影响的用例或命令记为“未执行”或“通过”写进报告。

1. 发出请求：标题写“需要你协助（第 N 步，来自 <主代理 / 子代理名>）”，按 H 编号逐条列出：看到的情况（有截图时附路径）；需要用户做什么（具体到命令、地址、窗口、按钮）；做完后回复什么；影响哪些用例或命令。同时有多条时一次列全。最后说明用户处理完后会接着做什么。
2. 发出请求后停下，等用户回复。
3. 用户回复后，以“继续”模式调用同一个子代理。调用时附上：原来的调用模式和全部原有输入；每条 H 的处理结果；上一次报告中已有结果的用例和命令。用户提供的登录信息只在调用子代理时传入，不写入方案文件、代码、报告或其他任何文件。用户的处理涉及偏离方案（例如改用可见 Chrome 执行某些用例），按第二步第 3 点同步更新方案文件。
4. 只有用户本人明确表示某项不处理（例如“跳过”“转手工”“转真机”）时，才能把相关用例记为“未执行（用户决定：……）”或“转真机验证”，并转到第六步的手工测试步骤。
5. 你自己的工具调用被权限确认拒绝时，同样按本节处理：说明被拒的工具和用途，询问用户是放行还是换一种做法。需要反复使用的，可以提示用户在项目的 `.claude/settings.json` 的 `permissions.allow` 中加入对应规则。

## 第一步：读取并检查方案

1. 没有提供路径时，列出 `docs/plans/` 与 `docs/superpowers/plans/` 下最近的几个方案文件，请用户指定，然后停下。
2. 读取计划并识别格式：
   - 独立方案：按既有要求检查状态、验收标准、待确认事项及答复、风险等级、修改文件、测试方案、检查命令和回滚方式；缺陷修复方案还要包含复现结论、根因和回归测试。
   - Superpowers 计划：检查任务清单、每项的文件和验证步骤，以及 `Frontend quality supplement (frontend-workflow)` 章节（旧计划中可能叫 `Frontend quality supplement (req-workflow)`，视为同一章节）。缺少前端补充时，先停下来，请用户运行 `/req-analysis <计划路径>` 后再执行。已批准的计划应由用户在调用本命令前确认。
   - 旧版方案没有“浏览器功能测试”时，按“不适用”处理，并在执行确认中说明。
3. 以下情况必须停下来提示，不要自行补写方案后直接开始改代码：
   - 文件不存在，或独立方案缺少必需章节，或 Superpowers 计划缺少任务、验证步骤或前端补充；
   - 独立方案状态为“含待确认项”；
   - 方案审核员的结论是“需要重做”，用户还没有决定怎么办：独立方案看状态是不是“方案需重做”，Superpowers 计划看前端补充的方案审核记录开头有没有“方案需重做：待用户决定”；
   - 方案状态为“已完成”（已经实现并出过报告）：说明情况，问用户要补做什么，不要重新实现一遍；
   - 独立方案的待确认事项中有既不是“已答复”、也不是“按假设处理”的条目；
   - 独立方案没有具体测试用例或“不适用”原因；Superpowers 计划的前端补充没有把 AC 映射到验证方式；
   - 缺陷修复方案的复现结论为“未复现”，且根因没有 A 级证据。
   Superpowers 计划由用户在调用本命令前确认批准；其设计文档中的未决问题仍需先解决。独立方案中标注为“按假设处理”的条目可以继续实现，但要在执行确认中列出这些假设。
4. 检查代码是否已偏离方案：独立方案或 Superpowers 计划有记录代码基准时，对比该提交号与当前代码（如 `git diff <提交号> --stat -- <计划涉及文件>`）。如果计划没有记录基准，跳过偏离检查，在下一步以当前 `HEAD` 作为实现基准，并把未提交代码改动列为实现前已有改动。计划涉及的文件在那个提交之后没有变动时直接继续。有变动时逐个看：只是行号移动、或改动与本方案的定位和改法无关的，在执行确认中列出后继续；改动让方案的定位、改法或验收标准不再成立的，停下来列出这些文件和冲突点，请用户选择——按当前代码调整方案后继续（按第二步第 3 点同步更新方案文件），或先重新运行分析命令更新方案。
5. 确定实现基准：
   - 方案文件中已经有“实现基准”记录时，说明之前开始过实现：不要覆盖，停下来询问用户是沿用原基准继续，还是重新开始。沿用时按“实现记录”里的“进度”小节接着做；旧方案没有这个小节时，对照 `git diff <实现基准>` 和实现记录判断做到了哪里。
   - 运行 `git status --porcelain`。独立模式排除 `docs/plans/` 和 `.claude/worktrees/`；Superpowers 模式只排除当前计划文件和 `.claude/worktrees/`。其他改动或未跟踪文件需列出，请用户先提交或暂存，或者明确回复“带着这些改动继续”。选择继续时，把这些文件记为“实现前已有改动”。
   - 运行 `git rev-parse HEAD`，把完整提交号记为“实现基准”。用文件编辑工具在方案文件末尾追加 `## 实现记录` 章节，写明实现基准和实现前已有改动的文件（没有就写“无”）。同时在其中建一个 `### 进度` 小节，并把文件开头的状态改为 `状态：实现中`（Superpowers 计划没有状态行，改为在“进度”小节的第一行写“状态：实现中”）。之后每完成一个任务、每一步结束、每轮审核结束时更新这个小节：当前在第几步，已完成和未完成的任务，审核到第几轮和未关闭的问题编号，本次运行的方式（有人值守或无人值守），无人值守运行时自己启动的后台进程（命令和端口；有人值守时页面由用户启动，写“无”）。它是上下文被压缩或会话中断后接着做的唯一依据，要写到别人拿着它就能继续的程度。
   - 之后传给子代理的基准一律是实现基准。方案中记录的提交号只用于上面第 4 点的偏离检查。
   - 不是 git 仓库时，实现基准记为“无”，子代理改为根据你提供的改动文件清单逐个阅读全文。
6. 把方案“修改的文件”逐个与项目规则中的高风险区域清单匹配，记下命中的文件。项目规则中没有清单、清单为空或仍是待填写状态时，记为“项目未配置高风险区域”。
7. 输出简短的执行确认：计划任务和文件、每个任务是“先写测试”还是“实现后补测试”（见第二步）、高风险区域、检查命令、浏览器验证方式与设备、审核方式（见第五步），以及预期的用户协助。调用本命令表示计划已批准；不再重复审批。
   本会话前面刚跑过 `/req-analysis` 或 `/req-bugfix`（对话里有分析阶段读过的源码和讨论）时，在执行确认末尾加一句：建议新开会话（或先 `/clear`；在 worktree 中只用 `/clear`）再运行同一条命令，方案文件已经写全了实现需要的结论，留在对话里的分析内容会在实现阶段每一步被重读。只是建议，不停下；用户在当前会话继续就照常做。无人值守运行不加这句。
   只有以下情况才停下来等用户确认，其余情况输出执行确认后直接开始：
   - 命中高风险区域的文件：逐个写明改动要点，请用户一次确认。确认后，实现中按这些要点修改不再逐个文件停下；超出这些要点的改动按第二步第 3 点处理。
   - 计划中有会在实现时让你停下来问用户的事项（例如计划步骤与项目规则冲突、规则或配置范围需要扩大）：在这里一并列出，不要等到做到那个任务时再单独问。计划的前端补充里已经由用户答复过的 D 编号事项，不再重复问。
   - 有“按假设处理”的条目、实现基准需要用户选择、或需要用户协助。
   - 方案文件中有“无人值守记录”章节（方案是无人值守运行产出的，其中的假设和安全关卡没有人确认过）：把“安全关卡放行”和“自动假设”的条目逐条列出，请用户一次确认。

## 第二步：实现

### 测试先行的范围

输出执行确认前读取 `${CLAUDE_PLUGIN_ROOT}/references/test-first-scope.md`，按其中的定义把每个任务归为“先写测试”或“实现后补测试”。方案或计划已经标注的按标注执行，不能把“先写测试”改成“实现后补测试”；没有标注的由你归类，并在执行确认中写明每个任务的归类和依据。

- “先写测试”的任务：按下面的 RED 流程，测试先于业务代码。
- “实现后补测试”的任务：由你先实现；连续的几个任务做完后，调用一次 `req-test-runner`，模式为“编写并运行”，一次补齐这些任务在计划中列出的测试。调用前按下文“实现前测试”第 1 点的要求写一份任务简报（另加这些任务已修改的业务文件及改动要点），把简报路径传给它。

任务要改的文件命中第一步第 6 点的高风险区域时，调用 `req-test-runner` 写测试（RED 或“编写并运行”）时把 Agent 工具的 `model` 参数设为 `opus`；其他调用用代理文件中的默认模型。

### 实现前测试（“先写测试”的任务）

每个“先写测试”的任务，在修改对应业务代码前先完成计划中适用的 RED 阶段。单元或组件用例由 `req-test-runner` 负责；已有 E2E 框架且计划选择 E2E 脚本时，由 `req-browser-tester` 负责 E2E 用例。两层都在计划中时，两者都要先验证失败。若只有浏览器手工验证，或测试框架不适用、无法自动验证，沿用已批准计划中的原因和手工步骤；不要为此自行新增依赖。

1. 调用 `req-test-runner`，模式为“编写并验证失败（RED）”，传入任务的 AC、单元/组件用例、文件、实现基准和实现前已有改动。只有浏览器手工验证时跳过此代理。相邻的几个任务互不依赖、接口已经确定时，合并成一次调用、一份简报；后续任务依赖前面任务的接口时，等接口确定后再写它的测试。
   调用前先写一份任务简报，把简报路径传给它。简报写入本机不提交的目录：Superpowers 计划用 `.superpowers/sdd/<计划文件名>/`（目录不存在时创建，并在其中放一个内容为 `*` 的 `.gitignore`），独立模式用 `docs/plans/briefs/<方案文件名>/`。简报的内容：
   - 该任务在计划中的原文（任务段落和对应的前端补充条目）；
   - 与该任务有关、已经定下的决策（用户的答复、执行确认中的约定、前面任务记下的裁决）；
   - 前面任务已经新增或修改的测试文件，以及每个文件的要点；
   - 要运行的测试命令。
   简报要写全到子代理不需要通读整份计划就能工作。
2. 计划选择 E2E 脚本时，在同一任务的业务代码修改前调用 `req-browser-tester`，模式为“编写并验证失败（RED）”。开始写页面、组件这类业务代码前，先看“进度”小节里有没有这个任务的 E2E RED 记录，没有就先补。页面做完再写的 E2E 容易照着实现写断言：规格写了而实现漏掉的文案、状态（例如“结果确认中”、只有一种币时的合计写法）就测不出来，要等代码审核发现，再走一轮修复、补测试和重跑。调用时传入 AC、E2E 文件路径、单次运行命令、访问地址、环境、设备和登录方式。若本地页面需要手动启动，先请用户按计划启动并确认；若测试脚本由现有 Playwright 配置启动页面，则按该脚本运行。RED 阶段只运行当前目标用例，不做全量浏览器检查。
3. 每条 RED 用例必须因行为断言得到与计划一致的失败，而不是语法、导入、mock 或环境错误。唯一的例外是被测的函数、组件或文件还不存在：这时每条新用例各自因“被测对象不存在”失败也算合格，但整个测试文件加载失败、连原有用例都跑不了的不算，要退回给子代理修正；实现记录里如实写是哪一种，不要都写成“按预期失败”。测试错误由负责的子代理修正后重跑；无法修正时停下来。手工浏览器验证不强求制造 RED，按计划保留实现前后的对照步骤。
4. 测试在实现前意外通过时停下来，检查是否覆盖尚未实现的行为；不得通过放宽断言或改动业务代码来制造失败。
5. 记录测试文件、每条用例的失败摘要和运行命令到计划的实现记录。缺陷修复还需记录复现截图；若方案没有“已复现”结论，或基准代码已经变化且涉及页面，先调用浏览器子代理重新复现。
   收到 RED 报告后，由你用 `cp` 把本次 RED 的测试文件复制一份，保存到简报所在目录下的 `red/<任务编号>/`（保持相对路径，文件名末尾加上 `.red`，例如 `price.test.js.red`），作为 GREEN 阶段核对断言没被改动的依据。加后缀是因为 `node --test`、Vitest、Jest 这类运行器会扫描整个项目里的 `*.test.*`，不改名的话快照会被当成测试再跑一遍，让检查失败。不要让测试子代理做这一步：钩子不允许它用 `cp`。

### 修改业务代码

可用技能中有 karpathy-guidelines（由 andrej-karpathy-skills 插件提供）时，在修改第一个业务文件前用 Skill 工具加载它，写和改业务代码时遵循，包括第三步至第五步里的修复。没有安装时跳过，按这一句执行：写最少的代码满足验收标准，不顺手重构，不加方案没要求的抽象和防御性代码。

它的原则里有三处和本技能的流程说法不同，都以本技能为准：
- “有疑问先问”：方案已经过用户批准，只有方案没有覆盖的新疑问才需要问，按下面第 3 点停下来；无人值守运行时按 `unattended-mode.md` 处理，不提问。
- “先写测试，再让它通过”：哪些任务先写测试按上文“测试先行的范围”；测试由 req-test-runner 和 req-browser-tester 写，你不写也不改测试文件。
- “循环到验证通过”：同一个问题修 3 次仍失败就停下来（第三步第 4 点、第四步第 8 点），不无限重试。

1. 只修改方案中列出的业务文件。测试文件由 req-test-runner 和 req-browser-tester 负责，你不修改。
2. 不做方案“不做什么”中排除的内容，也不顺手做“可选的局部整理与技术债”中的项目。
3. 实现过程中如果发现方案需要调整（要多改文件、接口要变、需要新增依赖、触及高风险区域等），先停下来说明原因和建议的调整，得到确认后再继续，并同步更新方案文件。
4. 对第一步第 6 点中命中高风险区域的文件，按第一步第 7 点在执行确认中一次确认。改动超出确认过的要点时，在修改该文件前停下来：说明具体改动，等用户确认后再改。
5. 方案的“参考资料”列了设计图规格或参考项目报告时，写对应页面和逻辑按报告文件来，只打开与当前任务有关的小节；不要再去通读参考项目，也不要直接打开设计图原图，那会把子代理替你省下的内容重新读进对话。规格里标“不确定”的值，按方案中对应待确认事项的答复处理；仍然没有答案、又必须看图才能决定时，只打开那一张图。
6. 使用第三方库的 API 或配置项、拿不准用法或版本差异时，如果可以使用插件自带的 Context7 服务，先按项目 package.json 中的版本查询文档；查询内容只写库名、版本和通用的技术问题，不写业务代码、内部接口地址、业务名称或账号信息。查不到时不要凭记忆硬写，在最终报告的遗留问题中注明。
7. “先写测试”的任务：完成 RED 后做最小实现，运行同一测试确认 GREEN；需要整理代码时再做 refactor，并再次运行测试。测试失败或计划步骤与代码不符时，先自己查一次；同一问题修了一次仍失败时，使用 `superpowers:systematic-debugging`（可用时）找根因，再更新计划中的执行记录。

## 第三步：单元测试与检查命令

1. 每个“先写测试”的任务完成后，由你自己确认 GREEN：
   - 运行该任务 RED 阶段的同一批目标测试，确认全部通过；
   - 把每个测试文件和 `red/<任务编号>/` 中同路径、带 `.red` 后缀的快照逐个 `diff`，确认测试文件没有被改动。有改动时停下来查原因：测试写错的，交 req-test-runner 修正并说明理由，不要自己改测试。
   该任务有 E2E RED 用例时，再调用 `req-browser-tester`“重新运行”，传入对应用例和失败结果。
   全部任务完成、“实现后补测试”的测试也已补齐后，由你自己按方案“检查命令”的原文依次运行一次完整检查，每条命令跑一次，不另派子代理。输出长的命令（全量测试、构建、E2E）把完整输出写到临时目录的日志文件里（如 `pnpm test > <临时目录>/test.log 2>&1; echo "exit $?"`），只读汇总行和失败的段落，需要细节时再按用例名或错误信息去日志里找。整段输出读进对话不会多发现问题，却会让之后每一步都带着它。全部通过就进入下一步。有失败时，先判断归因：明显是业务代码问题的由你修复后，重跑失败的那条命令和相关测试，到通过为止；测试代码问题或归因拿不准的，调用 `req-test-runner`“重新运行”，附上失败输出和要重跑的命令（失败的那几条），由它修正测试并归因。计划中的 E2E 验证仍按浏览器测试流程执行。不得在本阶段首次编写计划内测试；缺陷回归测试的断言和预期值不得修改。
   完整检查只在两个关口跑：这里一次，第六步写报告前按需一次。两者之间无论在哪一步修了代码，都只重跑失败的命令和受影响的测试，不把全部命令再跑一遍：跨文件的连带问题由结束前那一次兜住，每次修复都完整重跑并不能多发现什么，却会让一个小改动把全量检查跑上四五遍。这次完整检查跑完后，在“进度”小节记下它的结果；之后每次改动业务代码或测试文件，在同一处记一笔，第六步靠它判断要不要再完整跑一次。
2. 调用了 req-test-runner 时，阅读它返回的测试报告，按归因处理：
   - 业务代码问题：由你修复，然后自己重跑相关测试；同一问题修了一次仍失败、或根因不清时，使用 `superpowers:systematic-debugging`（可用时）找根因。全部修完后重跑之前失败的命令，不另派子代理。
   - 测试代码问题：req-test-runner 应已自行修正。如果它报告无法修正，判断原因；需要偏离方案时，按第二步第 3 点停下来说明。
   - 原本就失败：不修，记入最终报告。
   - 归因为“不确定”或你对归因有疑问时，自己阅读相关代码和测试核实，不要直接采信。确认是测试写错时，再次调用 req-test-runner 并说明理由，由它修正。
   - 它提出需要你决定的事项（如新增依赖、方案中的用例无法实现）：按第二步第 3 点停下来请示。
   - 需要用户协助：按“需要用户协助时”处理。
3. 你不得要求 req-test-runner 删除用例、跳过用例、放宽断言或为掩盖问题更新快照。缺陷修复方案的回归测试在修复后仍失败时，要修的是业务代码；确认是测试本身写错时，停下来说明，经用户同意后才能修改它的断言或预期值。
4. 同一个问题经过 3 次修复（包括你修业务代码和 req-test-runner 修测试）仍然失败，停下来，报告失败原因和已尝试的做法，等待指示。
5. 第三步完成的标准：每条检查命令都运行过，各自最后一次的结果（你自己运行的，或 req-test-runner 运行的）除“原本就失败”的条目外都是通过。因超时或输出不完整而记为“不确定”的命令，以及“待协助”的命令和用例，都不算通过：先核实原因，需要用户处理时按“需要用户协助时”处理。

## 第四步：浏览器功能测试（req-browser-tester 子代理）

方案的浏览器功能测试为“不适用”时跳过本步，在报告中写明原因。已有 E2E 框架并选择脚本时，RED 测试在第二步实现前完成；本步在第三步完成后执行浏览器验证：

1. 如实现前 RED 阶段已要求本地页面，沿用用户已启动的页面和实际地址；否则请用户按方案启动本地页面，给出启动命令和访问地址（方案的性能检查要求使用构建后的预览页面时，一并给出预览的启动命令和地址），然后停下，等用户确认已启动。用户告知的实际地址（例如端口被占用后自动换了端口）与方案不同时，以用户的为准，并更新方案文件。不要自己启动 dev server 或其他常驻进程。调用子代理前用 `git check-ignore -q docs/plans/browser-artifacts/x.png` 确认截图目录不会被提交；没有被忽略时（常见于 Superpowers 计划），按 `${CLAUDE_PLUGIN_ROOT}/references/plan-file.md` 里追加 exclude 的方式，在本机 git exclude 中追加一行 `/docs/plans/browser-artifacts/`。
2. 方案的登录方式需要测试账号或 token、而用户还没有提供时，向用户索取。只在调用子代理时传入，不写入方案文件、代码、报告或其他任何文件。
3. 方案中有用例使用“你正在用的 Chrome”（browser-user-chrome）时，先停下来征求用户同意：说明将在用户日常使用的 Chrome 中操作哪个访问地址、执行哪些用例、会用到用户已有的登录态，并提醒用户确认 Chrome 正在运行、已安装 Playwright Extension，连接时需要在扩展的授权页中选择一个标签页。用户明确同意后才能使用，同意只在本次 /req-implement 中有效（包括第四步和第五步中的重跑）；用户不同意时，这些用例记为“未执行（未获用户同意）”，转到手工测试。
4. 方案中有用例使用“可见 Chrome”（browser-chrome）时，告诉用户测试时会打开一个 Chrome 窗口，测试过程中不要在该窗口里操作；第一次需要登录时，子代理会停下来，请用户在该窗口中登录。
5. 调用前确认测试代码能通过类型检查：业务改动让已有测试或测试夹具跟着变（Hook 返回值、组件属性、接口类型加了字段）时，先由 req-test-runner 改完，并确认 `typecheck`（或项目的同类命令）通过，再调用 req-browser-tester。E2E 的构建通常先跑类型检查，两个子代理同时跑时，浏览器那边只会一遍遍构建失败。
   调用 req-browser-tester，模式为“执行”。调用时提供：方案文件路径、实现基准、访问地址、登录方式及用户提供的登录信息、用户是否已同意使用 browser-user-chrome（用到时）、本次修改的业务文件及每个文件的改动要点、要执行的用例（默认为方案中的全部浏览器用例）。方案的“参考资料”有设计图规格时，一并提供规格报告和设计图的路径，请它截图后对照规格核对布局、尺寸、颜色和状态，差异写进 `docs/plans/browser-artifacts/` 下的对照表。
6. 阅读它返回的浏览器测试报告，按归因处理：
   - 业务代码问题：由你修复业务代码，自己重跑与修复相关的单元测试（有失败时按第三步第 1 点处理），不完整重跑检查命令；再调用 req-browser-tester，模式为“重新运行”，附上修复说明，重跑失败的用例和与修复相关的用例。
   - 需要用户协助（页面打不开、浏览器未安装、需要登录或登录失效、验证码或 SSO 等需要本人操作的页面、browser-user-chrome 未获同意或连接失败、测试数据缺失、后端接口异常、工具调用被拒等）：按“需要用户协助时”处理（浏览器未安装时，给出报告中的安装命令）。不要自己安装浏览器或依赖。
   - 用例问题（方案中的步骤或预期不清楚、与验收标准矛盾、在模拟环境中无法执行）：按第二步第 3 点停下来说明，经用户确认后更新方案。只能在真机上验证的，经用户同意后转到手工测试步骤。
   - E2E 脚本本身写错：req-browser-tester 应已自行修正；无法修正时判断原因，必要时按第二步第 3 点停下来。
   - 原本就存在的问题（与本次改动无关的页面报错或失败请求）：不修，记入最终报告。
   - 归因为“不确定”、“不稳定”或你对归因有疑问时，自己阅读相关代码和截图等证据核实，不要直接采信。
7. 你不得要求 req-browser-tester 跳过用例、放宽预期或修改断言来通过测试。
   截图和截图对照由 req-browser-tester 查看，你读它的报告和它写在 `docs/plans/browser-artifacts/` 下的结论文件（如对照表 `diff.md`）。需要亲自核实某处时只打开相关的那一张，优先看局部截图，不要逐张打开整页长图：一张整页截图读进对话就有几十万字符，之后每一步都要带着它。
8. 同一个问题经过 3 次修复仍然失败，停下来，报告失败原因和已尝试的做法，等待指示。
9. 第四步完成的标准：没有“待协助”的用例；方案中的每个浏览器用例，在指定的每个设备上，最后一次结果都是“通过”；或经用户同意记为“转真机验证”；或因用户不同意使用 browser-user-chrome 记为“未执行（未获用户同意）”、因用户明确决定不处理记为“未执行（用户决定：……）”，并已转到手工测试。

## 第五步：独立代码审核

第四步完成后（或第四步不适用时，第三步完成后），调用 req-code-reviewer 子代理做一次完整审核。只派这一个审核员，不另派全分支审核、silent-failure-hunter、pr-test-analyzer 或其他审核代理；被吞掉的错误、不恰当的兜底和测试覆盖缺口由 req-code-reviewer 在同一次审核中检查。计划改动了页面或交互时，同一次审核里一并检查前端专项内容；没有改动页面或交互时，传入“本次不涉及页面，前端专项不适用”。

可用代理中没有 req-code-reviewer，或调用失败（例如网络中断、额度暂时用完）时，不要自己代替审核，也不要直接跳过：用同样的输入再调用一次。仍然失败时停下来说明原因，由用户决定换个时间再审，还是不审就结束；用户决定不审时，报告的审核结论写“审核未执行（用户决定：原因）”。这里和方案审核的做法不同（方案审核员调用失败时是跳过并注明）：方案之后还有用户审批和代码审核，而代码审核是改动交给用户前最后一道独立检查，所以多试一次，也不自行跳过。

0. 专项检查（可选，只在用户调用本命令时明确要求、且可用代理中有 `pr-review-toolkit:silent-failure-hunter` 和 `pr-review-toolkit:pr-test-analyzer` 时做，只在第 1 轮前做一次）：调用时提供实现基准、本次改动的文件清单和方案文件路径，说明“只读，不修改任何文件，不运行测试，只输出发现的问题及文件和行号”。结果不直接作为修改依据，作为“专项检查参考意见”交给 req-code-reviewer 复核。没做时在报告中写“未做（未要求）”。
1. 调用时提供：方案文件路径、实现基准、实现前已有改动的文件、本次改动的文件清单（你修改的业务文件，加上 req-test-runner 和 req-browser-tester 报告中新增或修改的测试文件）、命中高风险区域的文件、浏览器测试结果摘要（每个用例在每个设备上的结论、通用检查、性能与弱网检查和埋点核对的结论、转真机验证的项）、每个任务的归类（“先写测试”或“实现后补测试”，并注明是计划标注的还是你在执行确认中归类的）、审核轮次、运行方式（有人值守；或无人值守，这时附上方案“无人值守记录”中类别为“未执行”的条目）。输入是 Superpowers 计划时，写明“计划中的代码只作参考，以计划的文件、验收标准和‘不做什么’为准”。第 1 轮还要附上专项检查参考意见（做过时）。第 2 轮起，附上上一轮的问题清单，以及每条的处理结果（已修复 / 暂不处理 + 理由 / 有异议 + 理由），复核范围只写“上一轮问题及修复涉及的文件”和这些文件的清单。不要另加“重新审核全部改动”“补看上一轮没打开的文件”之类的要求：复核轮重读全部改动，用量和第 1 轮差不多；修复里出现的新问题，审核员在复核修复涉及的文件时就能看到。子代理看不到本次对话，它需要的信息必须在调用时写全。
2. 拿到审核报告后，开头有“需要用户协助”时，先按“需要用户协助时”处理，用户处理后重新审核本轮（不计入 2 轮上限）。然后逐条处理：
   - 阻断：必须处理，修复或提出异议。
   - 建议：在方案范围内且改动较小的，予以修复；否则记为“暂不处理”并写明理由。
   - 提示：不处理，原样记入报告。
   - 不认同的条目：标记为“有异议”并写明理由（引用代码、验收标准或方案内容作为依据）。不要为了通过审核而做不正确的修改。
   - 审核员对某条异议给出“维持”后，不要再次提出相同的异议：要么按审核意见修改，要么在结束时交给用户裁决。
3. 按问题所在位置分派修复：
   - 业务代码的问题：由你修复。
   - 单元测试或组件测试的问题：调用 req-test-runner，模式为“按审核意见修正”，附上对应的 R 编号和审核内容，并写明只重跑它改动的测试文件。
   - E2E 脚本或浏览器用例执行的问题：调用 req-browser-tester，模式为“按审核意见修正”，附上对应的 R 编号和审核内容。
   同一轮的修正攒齐了再派：先把这一轮的业务代码都改完，再把所有要改、要补的测试（审核意见涉及的、业务修复需要的回归测试）合并成一次 req-test-runner 调用、一份简报；E2E 同样合并成一次 req-browser-tester 调用，并按第四步第 5 点排在测试夹具改好之后。每新开一个子代理，它都要把相关代码从头读一遍，一轮里拆成三四次调用，用量就翻几倍。后续批次的简报只写本批新增的内容，注明前一份简报的路径。只补一两条用例、且这一轮调用过的子代理还能接着用时，用 SendMessage 让它继续，不新开一个。
4. 标注为“超出方案范围”的条目，或者修复需要多改文件、修改接口、新增依赖、触及高风险区域时，按第二步第 3 点处理：先停下来说明，得到确认后再继续，并同步更新方案文件。
5. 修复时遵守第二步至第四步的全部约束。尤其不允许为了通过审核或测试而删除用例、跳过用例、放宽断言。
6. 本轮有任何修复时：
   - 改了业务代码：自己跑相关测试，不完整重跑检查命令；修复涉及页面表现或交互时，再调用 req-browser-tester“重新运行”相关的用例。
   - 改了测试：对应的子代理在“按审核意见修正”时已重跑改动的测试，不用再重跑。
   按第三步第 1～5 点和第四步第 6～9 点处理结果。
7. 是否进入下一轮审核：
   - 本轮有阻断项被修复，或有“有异议”的条目：进入下一轮。第 2 轮起，只复核上一轮的问题清单和修复涉及的文件，不重新审核全部改动；调用时传入“复核范围：上一轮问题及修复涉及的文件”和这些文件的清单。
   - 本轮只修了建议项、没有阻断项和异议：不再复审，以第 6 点的检查结果为准，在报告中列出这些修复。
8. 结束条件：
   - 审核结论为“通过”，或按第 7 点不再复审：进入第六步。
   - 已完成 2 轮审核，仍有未解决的阻断项：停下来，列出这些条目、审核员的意见、你的理由和建议，等待用户决定。

## 第六步：测试与审核报告

写报告前先看“进度”小节：第三步那次完整检查之后，业务代码或测试文件改过（第三步里的修复、浏览器测试后的修复、审核后的修复都算）时，由你自己按方案“检查命令”的原文再完整运行一次，每条命令跑一次；没有改过就沿用第三步的结果，不重跑。这样交给用户的代码一定完整检查过。这一次有失败时按第三步第 1～4 点处理，修到通过；修复改了业务代码的，在报告的“代码审核记录”里写明“审核后有改动”和改动的文件、要点，因为这部分审核员没有看过。

在对话中输出以下内容，并追加到当前计划文件末尾的“## 实现、测试与审核报告”章节。风险等级为 L1、且不涉及页面的改动，不适用的小节各写一行“不适用”，不展开：

1. 修改清单：实际修改的文件，以及与方案的差异（没有差异就写“无”）。缺陷修复方案在这里加上缺陷修复记录：根因；修复前的证据（回归测试的失败摘要、复现截图）；修复后的证据（同一批回归测试通过、复现步骤在浏览器中出现期望结果）；同一根因的其他影响点及处理情况。
2. 单元测试与检查命令结果：以每条命令最后一次运行的结果为准，写明完整检查跑了几次、最后一次是在哪一步跑的、之后有没有再改过代码，列出每条命令及结果（通过 / 失败数量），附上关键输出摘要；并说明调用 req-test-runner 的次数。
3. 浏览器功能测试结果：方式和设备；每个用例在每个设备上的最后结果；通用检查（控制台报错、失败请求、横向溢出、点击区域）和埋点核对的结论；性能与弱网检查的指标和现象（有的话，注明是在开发服务器还是构建后的预览上测得）；截图等证据的路径；“不稳定”“转真机验证”和“未执行（用户决定）”的用例；过程中发出过的协助请求及处理结果；调用 req-browser-tester 的次数。不适用时写明原因。
4. 代码审核记录：审核员调用了几次；专项检查是否执行（未执行时写明原因）及其意见的采纳情况；审核轮数和最终结论；每条问题的编号、严重度和处理结果（已修复 / 暂不处理 + 理由 / 有异议 + 审核员最终结论）。“提示”级别的条目单独列出，供后续参考。
5. 用例与验收标准对照表：每条验收标准对应哪些单元测试、组件测试和浏览器用例，状态是“已自动化覆盖”“需手工验证”还是“未覆盖（附原因）”。
6. 待执行的手工测试步骤：可以直接交给测试同学使用，包含环境（真机型号、系统版本、App 版本）、数据准备、操作步骤、预期结果；包括转真机验证的项，以及浏览器模拟环境无法覆盖的检查点。
7. 回归测试清单：需要回归的功能点和场景。
8. 原本就失败的测试和原本就存在的问题：与本次改动无关的失败项和页面问题（没有就写“无”）。
9. 遗留问题与风险：未覆盖的部分、已知限制、建议后续补充的测试。如果有“按假设处理”的条目，逐条列出假设内容，以及假设不成立时需要修改的代码和测试。
10. 回滚方式：引用方案中的回滚方式，并补充本次实际改动需要注意的地方。

报告写完后更新方案文件开头的状态：审核结论为“通过”（或按第五步第 7 点不再复审）、检查命令全部通过时写 `状态：已完成`；用户决定不做代码审核、检查命令全部通过的，同样写 `状态：已完成`，并在下一行注明“代码审核未执行（用户决定）”；其他情况写 `状态：实现未通过`，并在下一行写一句原因。Superpowers 计划没有状态行时，把“进度”小节第一行的状态改成同样的写法。

不要自动提交（git commit）或推送代码，除非用户明确要求。

worktree 收尾（只在 worktree 中执行时）：在结束语后补充说明——
- 改动在 worktree `<路径>`（分支 `<分支名>`）中，还没有提交。归档本会话前要先提交，否则归档时选择丢弃会删掉这些改动。
- 需要提交时告诉我“提交”：我会根据方案和报告写好提交说明，经你确认后提交。推送由你执行。
- 并行任务的合并顺序和冲突风险，可以在主目录的会话中运行 `/req-parallel 状态` 查看。
- 合并完成后，停掉本 worktree 的本地页面，再归档会话。

结束时说明：“实现、测试和代码审核已完成（审核 N 轮，结论：……），报告已追加到 <方案文件路径>。请审阅改动。”审核未通过或没有执行时，开头改成如实的说法，例如“实现和测试已完成，代码审核未通过（N 条阻断项未解决）”或“实现和测试已完成，代码审核未执行（原因）”，不要写成已完成。
