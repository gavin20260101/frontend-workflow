# 生成无人值守任务书

把用户要做的事整理成一份任务书，交给 `/unattended` 运行。

写任务书时用户还在电脑前，这是**唯一能提问的时机**。`/unattended` 开始后没有人能回答问题，任务书里的每一处歧义都会变成“按假设处理”，假设错了就白跑一趟。所以这个技能的价值不在排版，而在两件事：把会改变“做什么”的问题现在问清楚；把无人值守时做不了的事现在挑出来。

先读 `${CLAUDE_PLUGIN_ROOT}/references/unattended-task-plan.md`，任务书的格式以它为准。

## 第一步：收集要做的事

来源按顺序看：命令附带的文字；用户给的文件路径（需求文档、方案文件、缺陷清单，读出来）；本次对话里用户已经说过要做的事。

什么都没有时，请用户说明要做哪些事，然后停下。

## 第二步：拆分和归类

把内容拆成任务。一个任务对应一次提交：能独立验收、独立回退。

- 太大的拆开：一个需求里有几块互不依赖的功能时，拆成几个任务。
- 该合的合上：几条描述指向同一个根因或同一处改动时，合成一个任务，免得后一个任务撞上前一个的改动。

每个任务判断类型：

| 看到什么 | 类型 |
| --- | --- |
| 描述的是现象、报错、“期望……实际……”、复现步骤 | `bugfix` |
| 给的是已经批准的方案文件路径 | `implement`（先确认文件存在） |
| 只要求验证或测试已有功能，不改代码 | `test` |
| 改文档、文案、不影响运行行为的配置这类不需要插件流程的小事 | `other`（会改到业务源码，或改 lint、类型检查、构建、依赖规则这类规则配置的，归为 `feature`：`other` 不经过测试和审核） |
| 其余要写代码的新功能、新页面 | `feature` |

拿不准是缺陷还是需求时问用户；`/unattended` 运行时归错了类，插件会终止这个任务。

## 第三步：轻量定位，只为排顺序

对每个代码任务，用搜索快速找出它大概会动哪些文件或模块。目的只有一个：判断任务之间有没有先后关系。

- 两个任务会改同一批文件，或一个要用另一个产出的东西：后者写 `依赖：T<n>`。
- 互不相干的任务写 `依赖：无`。失败的任务只会连带跳过依赖它的任务，所以不要随手加依赖。

到此为止。不要在这里设计方案、分析根因——那是 `req-analysis`、`req-bugfix` 在运行时做的事，这里做了也不会被采用。

## 第四步：挑出无人值守做不了的部分

读项目规则（`CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/` 下的文件和项目根目录的 `AGENTS.md`，存在的都读），对照下面的清单逐个任务看：

| 情况 | 怎么处理 |
| --- | --- |
| 整个任务都要靠本人在场（验证码或扫码登录后的页面、真实支付和短信、真机才能验证的行为、要用用户正在用的 Chrome） | 不排进任务书，列在“没排进去”里并写明原因 |
| 任务的一部分做不了（比如功能能写，但登录后的页面没法在浏览器里验证） | 照常排，在 `备注` 里写明哪部分会记为“未执行”并转手工 |
| 页面要登录后才能看到，而且可以用测试账号登录 | 不要把账号密码写进任务书。问用户要不要现在用可见 Chrome（browser-chrome）打开登录页、由用户登录一次：登录态会保留，无人值守时可以直接用。用户登录后，在 `备注` 里写“登录：用可见 Chrome 已保留的登录态”；项目规则写明了测试账号获取方式的，写“登录：按项目规则” |
| 任务要参考当前工作目录以外的项目源码 | 无人值守时没人能点权限确认，读不了就只能跳过。请用户现在把那个目录写进项目 `.claude/settings.local.json` 的 `permissions.additionalDirectories`（给出要加的路径，由用户自己改），在 `备注` 里写“参考项目：<路径>” |
| 任务附的设计图只有 Figma、蓝湖等链接 | 无人值守时不会登录这些网站。请用户导出图片放到本机，在 `备注` 里写“设计图：<本机路径>” |
| 任务依赖还没定的外部条件（项目文档里标着待平台答复、待登记的决策等） | 问用户：现在按什么假设做，还是先不排 |
| 任务会改项目规则里的高风险路径、规则配置，或要新增依赖 | 照常排。告诉用户这些在无人值守时会直接放行，并出现在汇总的“重点复核”里；用户不想放行的，在 `备注` 里写“不要改 <路径>”“不要新增依赖” |

## 第五步：提问

只问答案会改变“做什么”的问题，一次问完（用 AskUserQuestion，每个问题给出你推荐的选项）：

- 需求缺验收条件：什么情况下算做完。
- 缺陷缺复现步骤或期望结果：复现不了的缺陷，运行时会直接终止。
- 范围有歧义：影响哪些页面、哪些租户或主题、要不要兼顾某个旧行为。
- 第四步里需要用户定的事。

有合理默认做法的细节不要问，直接写进 `备注`，并在最后的输出里列出来，用户不同意可以改。问题多于 4 个时，先问最影响结果的 4 个，其余按默认写进 `备注`。

## 第六步：写任务书

按 `${CLAUDE_PLUGIN_ROOT}/references/unattended-task-plan.md` 的格式写。

- **输入保留用户的原话**，不改写、不总结。原话会原样传给插件，改写会丢信息。
- 提问得到的答案和补充的验收条件，接在原话后面，用“验收条件：”“补充：”分开，让人看得出哪些是原话、哪些是后补的。
- 验收条件写成“当……时，应该……”。
- 任务很大，或一次排了 4 个以上代码任务时，给最大的那几个加 `隔离：是`（一次运行最多 6 个）。
- 一次运行建议不超过 6 个代码任务。更多的分成两份任务书，分两次运行。

## 第七步：保存

文件名 `unattended-<YYYYMMDD-HHMM>.md`。`/unattended` 要求工作区干净，所以任务书必须放在 git 不跟踪的地方：

1. 默认放 `docs/plans/`。用 `git check-ignore -q docs/plans/<文件名>` 确认会被忽略。
2. 不会被忽略时，改放到 `<git rev-parse --git-common-dir 的输出>/unattended/plans/`（在 `.git` 里面，不影响工作区）。

不要为了放任务书去改 `.gitignore` 或 git 的排除设置。

## 第八步：输出

1. 任务一览表：编号、类型、标题、依赖、是否隔离。
2. 写进 `备注` 的默认假设，逐条列出，请用户过目。
3. 没排进去的事和原因。
4. 运行前要做的事：
   - 工作区要干净（现在不干净时直接指出有哪些改动）。
   - 权限模式切到“自动”。
   - 全局 `~/.claude/CLAUDE.md` 里要有“无人值守开关”一节；没有时 `/unattended` 会停下。
   - 要在 Claude 桌面应用里运行。
5. 运行命令：`/unattended <任务书路径>`。

到这里结束。不要自己开始执行任务，也不要替用户运行 `/unattended`：写任务书不等于授权无人值守运行，开关只认用户自己输入的命令。
