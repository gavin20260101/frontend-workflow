# 需求分析与方案

用户调用本命令时附带的文字，就是需求原文,或者提供了需求文件。如果没有附带任何文字，请用户提供需求原文，然后停下。

内容是缺陷报告（以 `bug` 开头、带有【Bug】标记，或者描述的是现象、报错、复现步骤）时，提示用户改用 `/req-bugfix <问题描述>`，然后停下；用户明确要求仍按需求处理时再继续。

分两个阶段进行，**每个阶段结束后都必须停下来，等待用户回复**。

全程只读，不修改任何业务代码、测试代码或配置文件。独立模式唯一允许写入的是阶段二末尾的 `docs/plans/` 方案文件，以及下文说明的本机 git exclude 文件；Superpowers 补充模式只允许更新用户指定计划中的 `Frontend quality supplement (frontend-workflow)` 章节。

下文的“项目规则”指项目中的 CLAUDE.md 和 CLAUDE.local.md（存在时）。

独立模式也应按 `references/frontend-quality-supplement.md` 考虑本次改动相关的 UI 状态、响应式断点、键盘与焦点、语义标签和既有设计系统；把适用项写入下方已有的验收、兼容和测试章节，不另造一份计划。

## Superpowers 计划补充模式

当输入是 Superpowers 的实施计划路径（通常位于 `docs/superpowers/plans/`；文件包含 Superpowers 的 Implementation Plan 结构和任务清单）时，直接进入补充模式，不重新做一份需求方案：

1. 读取该计划、它引用的设计文档、项目规则及相关实现代码，确认现有决定和本次改动范围。
2. 按 `references/frontend-quality-supplement.md` 补充 AC、UI 状态、适用的响应式与无障碍要求、测试映射、具体风险和回滚方式；每条 AC 至少映射到一种验证方式。沿用已有的计划编号和测试框架。
3. 把内容追加或更新在同一文件的 `## Frontend quality supplement (frontend-workflow)` 章节中。只修改该章节。计划中已有旧插件名下的 `## Frontend quality supplement (req-workflow)` 章节时，把它当作同一章节更新，并把标题改为新名称。
4. 逐个任务把计划要改的文件与项目规则中的高风险区域清单和规则配置文件对照，并检查计划步骤是否与项目规则冲突。把实现时会需要用户确认的事项一次列全：高风险文件的改动要点、计划步骤与项目规则冲突的地方、规则或配置范围需要扩大的地方。每项写明涉及的任务、原因和建议做法，编为 D 编号，一并放进未决问题。
5. 补充章节写好后，按 `references/plan-review.md` 调用 req-plan-reviewer 审核整份计划（方案类型为“Superpowers 计划补充”），处理意见；补充章节中已有“方案审核记录”且用户没有要求重新审核时跳过。
6. 输出新增或更新摘要、未决问题、计划文件路径，以及实际打开的项目文件、执行的搜索和查询的第三方文档。未决问题会改变需求或方案时先停下；用户答复后，把答复写进补充章节，不再单独问是否批准。结束时说明：“请审阅完整计划（含前端补充）。确认后直接运行 `/req-implement <计划路径>`，运行即视为批准计划和前端补充。”

- 保留 Superpowers 计划原有章节和任务；只改前端补充章节。
- 若补充章节已存在，更新它，不重复创建章节。
- 不另存到 `docs/plans/`，不改本机 git exclude，也不再单独要求用户审批这份补充。
- 若补充会改变需求、方案或工作范围，列出具体差异并停下；否则输出更新摘要，按第 6 点的结束语结束。不要另外询问“是否批准计划”：运行 `/req-implement` 就是批准。
- 这种模式供 Superpowers 的 brainstorming 和 writing-plans 产出草稿后、用户最终批准前使用。不要在这里再次调用 brainstorming 或 writing-plans。

输入是需求原文时，继续使用下方独立模式。安装了 Superpowers 的用户可先用它完成设计与实施计划，再把计划路径传给本命令补充前端要求。

## 并行工作区（worktree）

参数以 `--worktree` 或 `--worktree=<名字>` 开头时（/req-parallel 生成的第一条消息会带上它），先把本会话放进独立的 git worktree。参数中还可以带 `--base=<分支或提交>` 指定起点。去掉这两个参数后，剩下的才是需求原文：

1. 运行 `git rev-parse --git-dir` 和 `git rev-parse --git-common-dir`，两者不同说明已经在 worktree 中，跳过第 2～4 步。
2. 确定起点：参数中有 `--base` 时用它；没有时停下来，请用户在以下选项中选择，然后等待回复——
   - 远端默认分支：运行 `git symbolic-ref --short refs/remotes/origin/HEAD` 得到名字；取不到时不列这一项。
   - 当前分支：运行 `git rev-parse --abbrev-ref HEAD` 得到名字。
   - 其他分支或提交：由用户输入。
   用 `git rev-parse --verify <起点>^{commit}` 确认起点存在，记下提交号；不存在时请用户重新选择。当前目录有未提交的改动时提醒用户：这些改动不会带进 worktree。
3. 用 `git worktree list` 查看 `.claude/worktrees/<名字>` 是否已经存在，然后用 EnterWorktree 工具进入：已存在时传 `path` 进入它，并告诉用户这是继续使用已有的 worktree，跳过第 4 步；不存在时传 `name` 创建并进入。名字用参数中给出的；没有给出时用 `feat-<简短英文名>`（小写英文和连字符）。没有 EnterWorktree 工具时，请用户新开一个会话、打开输入框下方的 Worktree 开关后再运行本命令，然后停下。
4. 对齐起点（只针对第 3 步新建的 worktree）：运行 `git rev-parse HEAD`，与第 2 步记下的提交号相同就结束这一步。不同时，先确认 `git status --porcelain` 没有输出，再运行 `git reset --hard <记下的提交号>`，把这个新 worktree 的分支移到所选起点（只影响这个刚建好、还没有任何改动的 worktree；这个命令会请用户确认），完成后再用 `git rev-parse HEAD` 核对。`git status --porcelain` 有输出时不要执行，停下来说明情况。

只要当前在 worktree 中（包括用户用 Worktree 开关开的会话，判断方法同第 1 步），开始分析前先做环境检查：
- 本机 git exclude 中要有 `/.claude/worktrees/` 这一行：没有就按“保存方案文件”中追加 exclude 的方式追加（用文件编辑工具，已有就不追加），避免主目录把 worktree 当成未提交的改动。
- worktree 根目录下要有 node_modules：没有时给出命令（`cd <worktree 路径>`，再加上包管理器的安装命令，如 `pnpm install`），请用户在终端执行后回复，然后停下。不要自己安装。
- 访问端口：取本 worktree 在 `git worktree list` 中的序号 n（主目录为 0），建议端口为项目默认端口加 n（Vite 默认 5173），之后请用户启动本地页面时给出带端口的命令（如 `pnpm dev --port 5174`）。实际地址以用户启动后告知的为准。
- 方案“浏览器功能测试”的环境中写明 worktree 路径、分支名和实际访问地址。

输出要求：
- 相似实现、代码定位、影响范围中的每条结论，都按项目规则标注证据等级（A/B/C）。证据等级是唯一使用 A/B/C 的地方，修改的确定程度用“确定 / 可能 / 待定”。
- 项目规则没有定义证据等级时，使用默认定义：A = 打开文件看到了代码（附路径 + 函数名 + 行号）；B = 推断（写明依据和缺失的环节）；C = 代码中无法确定，需要向人确认。
- 证据等级为 C 的结论，同时列入待确认事项（Q 编号）。
- 每个阶段的输出末尾，列出实际打开过的文件和执行过的搜索（关键词 + 路径），以及查询过的第三方库文档（库名 + 版本 + 问题），放在该阶段规定的结束语之前。

## 查询第三方库文档

结论涉及第三方库（框架、组件库、工具库）的 API、配置项或版本差异时，如果可以使用插件自带的 Context7 服务（工具 `resolve-library-id`、`query-docs`），先查询：

- 版本以项目 package.json 中声明的为准，查询时带上版本。
- 查询内容只写库名、版本和通用的技术问题，不写业务代码、内部接口地址、业务名称或任何账号信息。查询会发送到 Context7 的服务器。
- 在结论中注明文档出处（库名 + 版本 + 文档条目）。文档说明的是库的行为，项目中的实际用法仍要打开代码确认，证据等级按项目规则标注。
- Context7 不可用（未连接、超出调用额度、查不到对应版本）时照常分析，在结论中注明“未查到对应版本文档”，不要凭记忆写成确定的结论。

## 阶段一：分析

输出以下内容：

1. 需求复述：一两句话。
2. 验收标准：编号列出（AC1、AC2……），写成“当……时，应该……”的形式。
3. 待确认事项：编号列出（Q1、Q2……），每一项写成需要向产品或后端确认的具体问题。没有待确认事项时写“无”。
4. 相似实现：项目中做过的类似功能（文件:行号），建议沿用它的写法。找不到真正相似的实现时写“未找到”，不要用关系不大的代码凑数。
5. 代码定位：需要修改的位置（文件:行号），每处标注修改的确定程度——
   - 确定：确定要改
   - 可能：可能要改，取决于实现方式（说明取决于什么）
   - 待定：取决于待确认事项的答复（注明对应的 Q 编号）
6. 影响范围：被修改的函数和数据在哪里被使用；是否影响埋点、公共接口、存储格式。
7. 测试现状：查看 package.json 和已有测试文件，说明项目用的测试框架（如 Jest / Vitest）、测试文件的存放位置和命名习惯，以及待修改代码目前有没有测试覆盖。如果项目没有测试框架，直接写明。
   可用的检查命令：逐个读出 test / lint / typecheck / build 等脚本的原文，并判断——
   - 包管理器：以项目规则中的声明为准；没有声明时，看根目录存在哪个锁文件（只看是否存在，不读取内容）。
   - 会修改文件的脚本（含 --fix、--write、-u、--updateSnapshot 等参数，包括通过 run-s / run-p 间接调用的子脚本）：不能作为检查命令，单独列出。
   - 会进入 watch 或常驻的脚本（如不带 run 的 vitest、jest --watch、react-scripts test、dev / serve）：写出单次运行的写法，优先加 `CI=true` 前缀，或追加单次运行参数（如 vitest 的 `--run`、jest 的 `--watchAll=false`）；脚本里写死了 watch、无法单次运行的，单独列出。
   浏览器测试条件：
   - 项目是否已有 E2E 框架（Playwright Test、Cypress 等的配置文件和依赖）及其单次运行脚本。
   - 启动本地页面的脚本（如 dev）和访问地址（看构建配置中的端口；Vite 默认为 http://localhost:5173）。
   - 待修改的页面是否需要登录，登录态从哪里来（页面登录、注入 token、开发环境免登录）。
   - 接口数据来自测试环境、本地 mock，还是需要在浏览器中拦截模拟。
   - 哪些功能依赖 App 环境（如 JSBridge、App 内登录），只能在真机上验证。
   拿不准的写成待确认事项。
8. 风险等级（初评）：逐项对照以下维度，取最高的一项作为等级——
   - 修改范围：单文件（L1）/ 同一模块内（L2）/ 跨模块（L3）
   - 是否触及项目规则中列出的高风险区域（把待修改的文件路径逐个与清单匹配）：是即为 L3。项目规则中没有高风险区域清单、清单为空或仍是待填写状态时，写明“项目未配置高风险区域”，不要当作未触及
   - 埋点：修改已有的事件名或属性名为 L3，新增为 L2
   - 用户感知：几乎无感（L1）/ 可感知（L2）/ 核心流程（L3）

如果歧义大到无法确定修改位置，输出到第 3 项就停下（之后的补全见“处理用户的答复”）。

阶段一结束时：
- 有待确认事项：说明“请提供待确认事项的答复，之后进入阶段二。暂时无法确认的条目，可以回复‘按假设处理’。”
- 没有待确认事项：说明“请确认验收标准，之后进入阶段二。”

## 处理用户的答复

- 每条待确认事项的状态记为以下三种之一：
  - 已答复：记录答复内容。
  - 按假设处理：用户明确同意先按假设推进时，写明“假设：……（待确认）”，以及假设不成立时需要改动的地方。
  - 未答复：用户没有回应，也没有同意按假设处理。
- 存在“未答复”的条目时，不进入阶段二，列出这些条目，请用户答复或同意按假设处理，然后停下。
- 不要自行把未答复的条目当作假设处理。
- 阶段一在第 3 项提前停止的：所有待确认事项都为“已答复”或“按假设处理”后，先补全阶段一的第 4～8 项，然后停下，说明“请确认补全的分析，之后进入阶段二。”补全中出现新的待确认事项时，按本节规则处理。

## 阶段二：方案审核单

在所有待确认事项都为“已答复”或“按假设处理”，且阶段一的第 1～8 项都已输出之后进行。

开头先列出“需要特别确认的事项”：方案涉及项目规则中的高风险区域、需要新增依赖（包括测试库和 E2E 框架）、修改公共接口，检查命令中有会修改文件、无法单次运行的脚本，浏览器测试需要的登录信息、测试数据、测试环境无法自动准备，或者浏览器测试需要使用你正在用的 Chrome（browser-user-chrome）时，逐项说明原因。没有就写“无”。项目没有测试框架时，不要自行安装，而是在这里提出，等用户决定。

然后输出：

0. 风险等级复核：结合答复重新评估风险等级。与初评不同时说明原因，之后一律以复核后的等级为准。
1. 修改目标：对应哪几条验收标准。
2. 修改的文件：逐个列出，说明改什么、为什么改、大致改几行。阶段一中标注为“可能”“待定”的位置，在这里要么确定修改，要么明确不改。
3. 不做什么：明确排除的内容。
4. 替代方案：至少一个，并说明为什么不选它。
5. 兼容性风险：老数据、老版本 App、其他调用方、数据团队的报表。
6. 埋点变更：逐条列出新增或修改的埋点——事件名、属性、触发时机，以及是新增还是修改已有埋点。修改已有事件名或属性名时，说明影响的报表。没有就写“无”。
7. 测试方案（必须具体到用例）：
   - 测试分层：用表格列出每条验收标准由哪几层验证（单元 / 组件 / 浏览器功能 / 真机手工）。每个场景放在能验证它的成本最低的一层；只有真实页面或真机才能验证的场景，才放到后两层。
   - 单元测试：列出要新增或修改的测试文件路径（沿用项目已有的目录和命名习惯）。每个用例写明：用例名、对应的验收标准编号、前置条件或 mock、输入、预期结果。按改动选择正常路径、关键边界、异常或错误路径；未覆盖的高风险场景写明原因与替代验证。项目没有测试框架、且用户决定不引入时，写“不适用”并说明原因，相关验收标准改为手工验证。
   - 集成或组件测试：如果项目已有这类测试，列出需要补充的场景；没有则写“不适用”并说明原因。
   - 浏览器功能测试：在模拟的手机浏览器中打开真实页面，按用户操作验证功能。
     - 方式：“E2E 脚本”（项目已有 Playwright Test 等框架时，沿用其目录和写法新增用例，列出文件路径和单次运行命令）/“浏览器验证”（项目没有 E2E 框架时，由浏览器测试子代理用插件自带的浏览器工具逐步执行，不新增依赖）/“不适用”（说明原因，例如改动不涉及页面）。
     - 环境：访问地址；启动命令（由用户在测试前手动启动，流程不会自行启动）；登录方式（只写方式，不写账号、密码或 token 本身，例如开发环境免登录、页面登录且测试账号由用户提供、在可见 Chrome 中手动登录一次、复用你正在用的 Chrome 的登录态）；测试数据和接口来源；需要在浏览器中模拟的接口返回（如空数据、接口失败、慢接口）。
     - 设备与浏览器服务：只为产品支持且受本次改动影响的平台指定，按风险与用户影响选择覆盖范围；使用无头、隔离的浏览器——iOS 用 browser-ios（WebKit 内核 + iPhone 15 模拟），Android 用 browser-android（Chrome 内核 + Pixel 7 模拟）。项目同时支持两者且改动影响两端时才都覆盖。以下两种只在需要时为具体用例指定，并写明原因：
       - 可见 Chrome（browser-chrome）：本机 Chrome 窗口 + Pixel 7 模拟，测试专用配置，登录态会保留。用于用户想看着测试执行，或需要在页面上手动登录一次后反复使用。
       - 你正在用的 Chrome（browser-user-chrome）：通过 Playwright 扩展连接用户日常使用的 Chrome，只能操作用户授权的标签页，带有用户真实的登录态，不做设备模拟。只用于必须复用已有登录态的场景（例如公司 SSO），并列入“需要特别确认的事项”。
       模拟环境不能代替真机，差异项放到手工测试步骤。
     - 用例：每个用例写明用例名、对应的验收标准编号、设备、前置条件、操作步骤、预期结果（页面上可见的状态）、需要核对的埋点请求（事件名和关键属性）。必须覆盖主流程、关键异常路径（如接口失败、空数据）和加载中状态。
     - 通用检查（每个用例都会做，不用逐条写）：控制台没有报错、没有意料之外的失败请求、页面没有横向溢出；移动端还会检查本次改动涉及的可点击元素尺寸。
     - 性能与弱网检查（可选）：只对 L3 改动或核心页面（如首页、列表页、下单页）写，由 browser-perf 服务（Chrome 官方的 DevTools MCP，本机 Chrome + 手机尺寸模拟）执行。每项检查写明：页面和操作；网络条件（如 Slow 3G、Fast 4G）和 CPU 降速倍数；关注的现象（加载中状态是否出现、有无白屏、超时和失败提示）；关注的指标（LCP、INP、CLS，不降速时的参考值为 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1）；是否做可访问性检查（Lighthouse）；是否检查内存泄漏（例如反复打开关闭同一个弹窗或页面）。开发服务器没有打包压缩，测得的指标只能看相对变化；需要准确数值时，写明使用构建后的预览页面（如 build 后 preview）及其启动命令和地址，同样由用户手动启动。
   - 检查命令：列出实现阶段要执行的完整命令（包括单次运行写法），只能基于 package.json 中已有的脚本。会修改文件或无法单次运行的脚本不列入，放到“需要特别确认的事项”。E2E 命令写在浏览器功能测试中，不放在这里。
   - 手工测试步骤：只列自动化测试（包括浏览器功能测试）覆盖不到的部分，例如真机 iOS Safari、App 内嵌 WebView、JSBridge、软键盘遮挡、刘海屏安全区、真实支付。编号列出操作步骤和预期现象，包括需要检查的埋点上报。项目规则列出了运行环境时，写明每个步骤需要在哪些环境验证。
   - 回归场景：L2 及以上必须列出；L3 必须覆盖所有受影响的调用方。
   - 基于假设的部分：如果有“按假设处理”的条目，说明假设不成立时哪些用例需要调整。
   - 无法自动化测试的部分：说明原因，以及用什么方式替代验证。
8. 回滚方式。
9. 可选的局部整理与技术债：单独列出，不放进修改范围。

## 保存方案文件

方案输出后，将完整方案写入 `docs/plans/YYYYMMDD-简短英文名.md`（日期为当天，英文名用小写和连字符，例如 `20261025-order-coupon-limit.md`）。目录不存在就创建；同名文件已存在且不是本需求的方案时，在文件名末尾加 `-2`、`-3`，不要覆盖。

写入前，先判断方案文件会不会被提交进仓库（以下 git 命令都是只读的）：
1. 运行 `git rev-parse --is-inside-work-tree`。失败说明不是 git 仓库：跳过本判断，在输出中注明。
2. 运行 `git ls-files -- docs/plans/`。有输出说明该目录已有文件被仓库跟踪：不要修改 git 配置，也不要执行 git rm，停下来告诉用户“docs/plans/ 已被仓库跟踪”，由用户决定是否继续写入。
3. 运行 `git check-ignore -q docs/plans/<文件名>.md`（文件还不存在也可以判断）：
   - 退出码 0：已被忽略，直接写入。
   - 退出码 1：未被忽略。运行 `git rev-parse --show-prefix` 和 `git rev-parse --git-path info/exclude`，用文件编辑工具（不用 echo 等终端命令）在 exclude 文件末尾追加一行 `/<前缀>docs/plans/`：前缀为空时就是 `/docs/plans/`；文件不存在就新建；已有相同的行就不追加；不改动原有内容。然后再运行一次 check-ignore，确认退出码为 0，并在输出中说明“已在本机 git exclude 中忽略 docs/plans/，只影响本机，不修改 .gitignore”。

文件开头写明状态和类型：
- `状态：含待确认项`：存在“需要特别确认的事项”，且用户尚未确认。
- `状态：待审批`：其他情况。
- `类型：需求`。

文件必须包含以下章节，供 /req-implement 读取：

- 状态和类型
- 需求原文
- 验收标准（AC 编号）
- 待确认事项及答复（Q 编号，逐条写明状态：已答复 + 答复内容，或按假设处理 + 假设内容）
- 风险等级（初评、复核结果及依据）
- 测试现状
- 需要特别确认的事项
- 阶段二的全部内容（0～9 项）
- 方案依据的代码版本：执行 `git rev-parse --short HEAD` 记录当前提交号；不是 git 仓库时写“无（非 git 仓库）”

用户对方案提出修改意见时，更新同一个文件，不要新建。用户确认了“需要特别确认的事项”后，把状态改为 `待审批`。

## 方案审核

方案文件首次保存后，按 `references/plan-review.md` 调用 req-plan-reviewer 审核一轮并处理意见，然后再给出阶段二的结束语。

阶段二结束时，说明：
“方案已保存到 <文件路径>。请审阅方案，批准后在新会话或当前会话中运行 /req-implement <文件路径> 开始实现。在此之前，我不会修改任何代码。”

如果状态为“含待确认项”，改为说明：
“方案已保存到 <文件路径>，其中有需要特别确认的事项（见开头）。请先确认这些事项，我会更新方案状态，之后才能运行 /req-implement。”
