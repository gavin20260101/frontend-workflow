# 开关打开后，项目规则怎么处理

依据用户全局 `~/.claude/CLAUDE.md` 的“无人值守开关”。原则：项目规则里“等人确认、由人评审、由人执行”的条款，改为直接执行并记录；规则里对**代码本身**的要求（分层、依赖方向、编码约定、检查要通过）一条都不放开。

不同项目的规则不一样。下表列的是常见条款，你的项目按同样的思路归类：先判断条款属于“要人点头”还是“代码要满足”，只有前一种放开。

## 对照表

| 项目规则的条款 | 常见出处 | 开关打开后的做法 | 记录什么 |
| --- | --- | --- | --- |
| AI 不自动提交 | 项目规则的 Git 一节 | 核验通过后提交到 `auto/` 分支 | 提交号 |
| 涉及多层或要改契约的需求，先给计划、确认后再改 | 任务类型的最低流程 | 方案由插件 `--auto` 产出并经它的方案审核员审核，不等人确认，直接实现 | 方案路径 |
| 高风险路径的改动要点由人批准 | 高风险区域清单 | 按方案改；超出方案要点时也继续，写明超出了什么、为什么 | 每个文件的改动要点 |
| 规则配置的改动要架构负责人评审 | 规则配置一节 | 只有任务本身需要时才改（例如新规则、新契约测试）；写明对应的规则编号 | 文件、改了什么、对应规则 |
| 新增第三方依赖先说明、等确认再装 | 依赖安装一节 | 只装方案写明的那一个，精确版本，用锁文件对应的包管理器 | 包名、版本、浏览器支持范围、声明的框架版本范围 |
| 不主动安装依赖 | 用户全局规则 | `node_modules` 缺失时按锁文件安装（如 `pnpm install --frozen-lockfile`） | 执行的命令 |
| 与方案冲突或方案没覆盖时停下说明 | 修改中禁止的做法 | 采用你原本会向用户建议的最小必要变更，继续 | 冲突的规则编号、原因、采用的变更 |
| 改层的职责、依赖方向或规则，先登记决策再改 | 方案的决策一节 | 先在方案里登记一条决策，标注“（无人值守登记，待 <架构负责人> 复核）”，再改规则配置和代码 | 决策编号和内容 |
| 契约变更需要评审（配置字段、Schema、主题、扩展点） | 契约变更清单 | 按清单把要一起更新的地方都更新 | 改了哪些契约 |
| AI 不自行登记临时例外 | 例外一节 | 确实无法遵守规则时登记：字段按项目要求填全，期限不超过项目上限，批准人写“待 <架构负责人> 复核（无人值守）” | 例外编号、规则、范围、原因 |
| AI 不自行登记第三方命中 | 已知事项、第三方命中一节 | 给出走不到的依据后登记，批准人同上 | 包名、版本、依据 |

例外是最后的手段：先试着让代码符合规则，确实做不到才登记。登记例外来让自己写的违规代码通过，属于削弱检查，不在开关范围内。

## 不放开的

- 分层、依赖方向、编码约定、兼容性要求等对代码的要求。
- 检查必须通过。检查不过就修代码；修不好如实记为失败。
- 证据等级、汇报格式、先写测试的范围。
- 提交说明的格式要求（包括不加 AI 署名）。
- 用户权限设置里禁止或要询问的命令（如 `git push`、`curl`、`sudo`）。

## 记录格式

插件流程里的决定，由插件写进方案文件的“无人值守记录”（U 编号）。插件之外由你做的决定（提交、`other` 类任务里的放行、登记的例外和决策），写进运行目录的 `state.md`，汇总时归到“重点复核”，编号用 K1、K2……（R 留给代码审核的问题编号）：

```markdown
- K1（T2，高风险路径）：改了 `src/config/schema.ts`，新增可选字段 `brand.slogan`。
  - 原本要求：Schema 改动需架构负责人评审（写上项目规则里的条款或编号）。
  - 依据：方案 docs/plans/20261116-xxx.md 第 3 节。
  - 复核要点：字段是否该进 Schema；`schemaVersion` 没有加 1，因为只新增了可选字段。
```

每条都要写“复核要点”：这个决定不成立时，要改回哪些地方。
