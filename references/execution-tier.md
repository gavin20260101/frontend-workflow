# 执行档位

同一套流程，难度不同的方案适合用不同的模型和思考程度：钱、权限、状态机这类改动值得用最强的模型一次写对；文案和样式改动用中档就够，多花的用量换不来什么。档位在写方案时定下（`/req-analysis`、`/req-bugfix`），实现时（`/req-implement`）和无人值守编排时（`/unattended`）照着用。

模型只写别名：`fable` > `opus` > `sonnet` > `haiku`，从强到弱、从贵到便宜。思考程度：`low` < `medium` < `high` < `xhigh` < `max`。

## 怎么定档

按下面的顺序对照，命中第一条就是那一档：

| 档位 | 命中条件（任一） | 主会话（实现） |
| --- | --- | --- |
| A | 风险等级 L3；命中项目规则的高风险区域；涉及钱、支付、权限、合规或“失败关闭”；涉及并发、重试、单飞、定时刷新、实时连接、会话令牌这类状态机；缺陷根因在时序或环境差异 | `fable`，`high` |
| C | 风险等级 L1，并且只改文案、Token 或样式取值、单个组件的视觉、文档 | `opus`，`medium` |
| B | 其余 | `opus`，`high` |

- 拿不准时取高一档：返工一轮的用量，比高一档多花的还多。
- A 档也用 `high`，不用 `xhigh`：更高的档位收益不稳定，只在方案里点名的个别任务（例如支付的失败关闭）写明用 `xhigh`。
- 拆成几份子方案时，每份子方案各定各的档位，总方案不写。

## 写进方案文件

方案的阶段二末尾（“回滚方式”之后）加一节：

```markdown
## 执行档位

- 档位：A（命中：涉及钱包扣款的失败关闭；src/capability/ 是高风险区域）
- 主会话：fable，high
- 方案审核、代码审核第 1 轮：fable，high
```

“命中”写清是哪一条条件、对应哪个文件或 AC，方便用户判断要不要改档。用户在审批时要求改档的，照用户的改，并在“命中”后注明“用户指定”。

Superpowers 计划补充模式写在补充章节里，用 `### 执行档位` 小节，内容相同。

## 子代理按档位调用

子代理文件里写的模型是 B 档的默认值。调用 Agent 工具时传 `model`、`effort` 参数会覆盖它，只在下表和默认值不同时才传。Agent 工具不接受 `effort` 参数时（Claude Code 低于 v2.1.292），只传 `model`。

| 子代理与时机 | A | B | C |
| --- | --- | --- | --- |
| `req-plan-reviewer` | `fable`，`high` | 默认（`opus`，`high`） | 默认 |
| `req-code-reviewer` 第 1 轮 | `fable`，`high` | 默认（`opus`，`high`） | `opus`，`medium` |
| `req-code-reviewer` 第 2 轮起（只复核上一轮的问题） | 默认（`opus`，`high`） | 默认 | `opus`，`medium` |
| `req-test-runner` 写 RED 测试，任务属于业务行为、出错路径或缺陷回归 | `opus` | `opus` | 默认（`sonnet`） |
| `req-test-runner` 其他模式（补写测试、重新运行、按审核意见修正） | 默认（`sonnet`） | 默认 | 默认 |
| `req-browser-tester` | 默认（`sonnet`） | 默认 | 默认 |
| `req-browser-tester` 对照设计图核对截图 | `effort: high` | `effort: high` | `effort: high` |

为什么这样分：

- 方案审核在 A、B 两档并不是可有可无，但它之后还有用户审批和代码审核兜底，所以只有 A 档升到 `fable`。第 1 轮代码审核是改动交给用户前唯一一次完整的独立审核，A 档同样用 `fable`；第 2 轮起只看上一轮的问题和修复，范围小，`opus` 够用。
- RED 测试就是可执行的规格：规格里写了的状态、文案、失败路径，RED 用例写全了，实现漏掉时测试就会失败，不必等审核员来发现、再走一轮修复和复审。所以业务行为类的 RED 用 `opus`；补测试、修时序这类跟着实现走的工作用 `sonnet`。
- 任务要改的文件命中高风险区域时，`req-test-runner` 不管哪个模式都用 `opus`（`/req-implement` 第二步原有的规定，与本表不冲突，取高的）。

`req-context-reader` 的模型在 `context-reader.md` 的“选模型”里定，和档位无关：它在定档之前就会被调用。

## 实现开始时核对主会话

`/req-implement` 第一步读方案的“执行档位”，和当前会话的模型、思考程度比较：

- 当前模型：Claude 桌面应用里用 `mcp__ccd_session_mgmt__get_session` 查 `"self"`，读 `model` 字段；没有这个工具时，看系统提示里写的“你由哪个模型驱动”。思考程度读不到时，按读不到处理，只提醒、不判断高低。
- 当前模型比档位要求的低：
  - A 档：在执行确认里停下来，说明档位、命中条件和当前模型，请用户二选一：切换后重新运行同一条命令（命令行用 `/model <别名>`、`/effort <级别>`，桌面应用用消息框的模型菜单；切换只从下一条消息起生效，所以要重新发一次命令），或者回复“按当前模型继续”。
  - B、C 档：在执行确认里写一句，不停下。
- 当前模型比档位要求的高：在执行确认里写一句“本方案是 X 档，换成 <模型> 可以省用量”，不停下。
- 方案没有“执行档位”一节（旧方案）：按上面“怎么定档”用方案里的风险等级、高风险区域和修改的文件推定，在执行确认里写明“按规则推定为 X 档”，之后子代理照推定的档位调用。

无人值守运行（`--auto`）时都不停下：把当前模型和档位写进无人值守记录，按当前模型继续，子代理照档位调用。
