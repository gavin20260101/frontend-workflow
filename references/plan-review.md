# 方案审核（req-plan-reviewer）

方案文件保存后、交给用户审批前，调用一次 `req-plan-reviewer` 子代理（使用 Fable 模型）审核方案。只审核一轮，不循环复审。

## 调用

调用时提供：方案或计划文件路径、方案类型（需求 / 缺陷修复 / Superpowers 计划补充）、方案依据的代码版本。子代理看不到本次对话，它需要的信息必须写全。

可用代理中没有 `req-plan-reviewer`，或调用失败（例如当前账号无法使用 Fable 模型）时，跳过审核，在输出中写明“方案审核未执行：原因”，照常结束本阶段。不要改用其他模型或自己代替审核。

## 处理意见

报告开头有“需要用户协助”时，先转达给用户，处理后重新调用。然后逐条处理 P 编号的意见：

- 不改变需求或范围的“必须修改”和“建议”：自己打开对应代码核实。成立的直接更新方案文件；不成立的标记“不采纳”并写明理由（引用代码或需求原文）。不要不加核实地照搬。
- 改变需求、AC 或范围的意见：不直接改方案，编为 Q 编号列入待确认事项，由用户决定。
- “提示”：不处理，原样记录。
- Superpowers 计划补充模式：只能修改 `Frontend quality supplement (frontend-workflow)` 章节；补充章节以外的意见列入未决问题，由用户在 Superpowers 计划中处理。

在方案文件中追加或更新 `## 方案审核记录` 章节（Superpowers 计划补充模式改为补充章节内的 `### 方案审核记录` 小节，不新增顶级章节）：审核结论，以及每条意见的编号、摘要、处理结果（已采纳 / 不采纳 + 理由 / 转为 Q 编号）。用户之后再修改方案时，不再重新审核，除非用户要求。

## 输出

在本阶段的结束语之前，输出审核结论和处理摘要（已采纳几条、不采纳几条及理由、新增了哪些待确认事项）。新增了待确认事项时，按“处理用户的答复”的规则停下等用户答复，答复后更新方案文件，再给出本阶段的结束语。
