# 方案审核（req-plan-reviewer）

方案文件保存后、交给用户审批前，调用一次 `req-plan-reviewer` 子代理审核方案。只审核一轮，不循环复审。模型和思考程度按方案“执行档位”一节和 `${CLAUDE_PLUGIN_ROOT}/references/execution-tier.md` 的“子代理按档位调用”：A 档在调用时传 `model: fable`、`effort: high`，B、C 档用子代理文件的默认值（Opus，high）。

## 调用

调用时提供：方案或计划文件路径、方案类型（需求 / 缺陷修复 / Superpowers 计划补充）、方案依据的代码版本。子代理看不到本次对话，它需要的信息必须写全。

可用代理中没有 `req-plan-reviewer`，或调用失败（例如网络中断、额度暂时用完）时，跳过审核，在输出中写明“方案审核未执行：原因”，照常结束本阶段。不要改用其他模型或自己代替审核。方案之后还有用户审批和代码审核，少这一轮可以接受；代码审核是改动交给用户前最后一道独立检查，所以 `/req-implement` 对代码审核员的做法不同，会再调用一次。

## 处理意见

报告开头有“需要用户协助”时，先转达给用户，处理后重新调用。然后逐条处理 P 编号的意见：

- 不改变需求或范围的“必须修改”和“建议”：自己打开对应代码核实。成立的直接更新方案文件；不成立的标记“不采纳”并写明理由（引用代码或需求原文）。不要不加核实地照搬。
- 改变需求、AC 或范围的意见：不直接改方案，编为 Q 编号列入待确认事项，由用户决定。
- “提示”：不处理，原样记录。
- 结论为“需要重做”，或有“必须修改”的意见既没有采纳、也拿不出不采纳的依据：不要自己重写方案再审一轮。把方案文件的状态写成 `方案需重做`（Superpowers 计划没有状态行，改为在补充章节的方案审核记录开头写一行“方案需重做：待用户决定”），在本阶段的结束语之前单独说明审核员的结论和这些意见，由用户决定按意见重做还是按原方案继续。用户决定按原方案继续时，把状态改回 `待审批`（Superpowers 计划把那一行改成“用户决定按原方案继续”），并在方案审核记录里写明这是用户的决定。带 `--auto` 时没有人能决定，按 `unattended-mode.md` 中结束块的定义，把结果写成“未完成”。
- Superpowers 计划补充模式：只能修改 `Frontend quality supplement (frontend-workflow)` 章节；补充章节以外的意见列入未决问题，由用户在 Superpowers 计划中处理。

在方案文件中追加或更新 `## 方案审核记录` 章节（Superpowers 计划补充模式改为补充章节内的 `### 方案审核记录` 小节，不新增顶级章节）：审核结论，以及每条意见的编号、摘要、处理结果（已采纳 / 不采纳 + 理由 / 转为 Q 编号）。用户之后再修改方案时，不再重新审核，除非用户要求。

## 输出

在本阶段的结束语之前，输出审核结论和处理摘要（已采纳几条、不采纳几条及理由、新增了哪些待确认事项）。新增了待确认事项时，按“处理用户的答复”的规则停下等用户答复，答复后更新方案文件，再给出本阶段的结束语。
